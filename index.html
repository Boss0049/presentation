22 หน้า เริ่มจากศูนย์ ไม่ต้องมีพื้นฐาน ตัวอย่างจริงจากโปรเจกต์ jobportal-ui

ลองนึกภาพ: เราสอน Claude ว่าโปรเจกต์นี้ใช้ Vite, เทสต์อยู่ใน src/__tests__/, ชอบ named export มากกว่า default export และ dev server รันที่พอร์ต 5173 ระหว่างเซสชันนั้น Claude ทำได้สวยงามมาก แต่พอเปิดเซสชันใหม่วันถัดไป — เหมือนคุยกับเพื่อนร่วมงานที่ เป็นโรคความจำเสื่อมทุกคืน ต้องอธิบายทุกอย่างใหม่หมด

ทางเลือกที่แย่ พิมพ์อธิบายซ้ำทุกเซสชัน — เสียเวลา ไม่ scale และลืมง่ายว่าเคยบอกอะไรไปแล้วบ้าง

เอกสารชิ้นที่ 1

CLAUDE.md (คู่มือพนักงานใหม่)

เขียนโดยเรา (คนที่ดูแลโปรเจกต์) · อ่านทุกเซสชันแบบไม่มีข้อยกเว้น · แชร์ให้ทีมผ่าน Git

เหมือนตอนพนักงานใหม่เข้าออฟฟิศวันแรก HR จะยื่น คู่มือพนักงาน ให้เล่มหนึ่ง — กฎการแต่งตัว, ชื่อระบบที่ใช้, ขั้นตอนเบิกของ ฯลฯ Claude Code ก็มีเล่มเดียวกันนี้ชื่อว่า CLAUDE.md

  • ใครเขียน: เรา (คนพัฒนา) เป็นคนพิมพ์เอง ไม่ใช่ Claude
  • โหลดเมื่อไหร่: ทุกเซสชัน ทุกครั้ง ไม่ว่างานที่ทำจะเกี่ยวข้องหรือไม่
  • แชร์ทีม: ใช่ — commit เข้า Git ทุกคนในทีมอ่านเล่มเดียวกัน
  • ใส่อะไรดี: ภาพรวมโปรเจกต์, tech stack, คำสั่ง build/test, สถาปัตยกรรมคร่าวๆ, กฎ coding ที่ใช้ทั้งโปรเจกต์, workflow ของ Git
แต่แล้วปัญหาก็มา

คู่มือหนา 400 บรรทัด = ทุกอย่างสำคัญเท่ากันหมด

ลองนึกภาพ CLAUDE.md ของเราโตขึ้นเรื่อยๆ จนมีกฎ React, guideline API, คำเตือนเรื่อง database migration, นโยบาย security และข้อกำหนดการเขียนเทสต์ ปนกันอยู่ในไฟล์เดียว พอ Claude กำลังแก้ React component มันก็ยังต้อง "แบก" กฎ migration กับ security ติดหัวไปด้วยทั้งที่ไม่เกี่ยวเลย พอทุกกฎ สำคัญเท่ากันหมด ผลคือไม่มีข้อไหนได้รับความสนใจเป็นพิเศษเลย ความสนใจของ Claude ก็เจือจางกระจายไปทั่ว

อุปมา จะไปซ่อมก๊อกน้ำรั่วแค่ตัวเดียว แต่ต้องแบกทั้งกล่องเครื่องมือ — เลื่อยโซ่, ชุดเชื่อม, พู่กันทาสี — ติดตัวไปด้วยทุกครั้ง ทั้งที่ใช้จริงแค่ประแจตัวเดียว
ผลที่ตามมา เราแก้ไฟล์ CLAUDE.md ยากขึ้นเรื่อยๆ เพราะต้องอ่านทำความเข้าใจทั้ง 400 บรรทัดก่อนแก้ไขจุดเดียว และพื้นที่ในหัวที่ Claude ใช้คิดในตอนนั้น (เรียกว่า context) ก็ถูกกินไปกับข้อมูลที่ "ไม่เกี่ยว" กับงานตรงหน้า
เอกสารชิ้นที่ 2

Rules (กฎของแผนก)

แทนที่จะยัดทุกอย่างไว้ในคู่มือเล่มเดียว ก็แยกเป็น "กฎของแต่ละแผนก" เก็บคนละแฟ้ม หยิบมาอ่านเฉพาะตอนเข้าไปทำงานแผนกนั้นจริงๆ

กฎกลาง — ทุกแผนกต้องอ่าน

แฟ้มนี้ไม่ได้ระบุว่า "เฉพาะแผนกไหน" ก็เลยแจกให้ทุกแผนกอ่านเหมือนกันหมด ทุกเซสชัน เหมาะกับกฎที่ใช้ทั้งโปรเจกต์

# code-style.md (ไม่ระบุแผนก = แจกให้ทุกแผนก)
- เขียนคอมเมนต์อธิบายโค้ดเป็นภาษาอังกฤษเสมอ
- ตั้งชื่อตัวแปรให้สื่อความหมาย อ่านแล้วเข้าใจทันที
- ห้ามลบไฟล์โดยไม่ถามก่อน
กฎแผนก API เท่านั้น

แฟ้มนี้ระบุชัดว่า "แผนกไหนถึงจะได้ใช้" (ในที่นี้คือโฟลเดอร์ของฝั่ง API) → คนแผนกอื่นจะไม่ถูกแจกแฟ้มนี้ไปอ่านให้เสียเวลา

- ตอบกลับ error ให้อยู่ในรูปแบบเดียวกันทุกครั้ง
- บันทึก log ทุกครั้งที่มีคนเรียกใช้งาน

ที่เก็บ: โปรเจกต์เดียว → .claude/rules/ · ใช้ได้ทุกโปรเจกต์ → ~/.claude/rules/ แถมสร้าง sub-folder ได้ เช่น database/migrations.md, database/queries.md

Auto Memory (MEMORY.md) — สมุดจด
  • เขียนโดย Claude เอง อัตโนมัติ
  • เก็บสิ่งที่ "เรียนรู้" จากการคุยกัน
  • อยู่ในเครื่อง ไม่แชร์ใคร
  • อุปมา: สมุดจดส่วนตัวของนักเรียน

เปิดใช้งาน เป็นค่าเริ่มต้น ไม่ต้องติดตั้งอะไรเพิ่ม เก็บไว้ที่ ~/.claude/projects/<project>/memory/ — ที่จัดเก็บผูกกับ git repo ไม่ใช่ branch ดังนั้นทุก branch/worktree ของโปรเจกต์เดียวกันใช้สมุดเล่มเดียวกัน

ของจริง: ตอนบอกว่า "ให้เว้นระยะด้วย tab ไม่ใช่ space"

ดูสมุดโน้ตของ Claude ตอนกำลังจดจริงๆ

พิมพ์บอก Claude สั้นๆ ว่า "จำไว้ด้วยว่าโปรเจกต์นี้เว้นระยะด้วย tab ไม่ใช่ space นะ" หน้าจอจะโชว์ข้อความ Writing memory — Claude กำลังค้นก่อนว่ามี memory.md อยู่แล้วหรือยัง ถ้าไม่มีก็สร้างใหม่ แล้วเขียนไฟล์รายละเอียดแยกออกมา พร้อมให้ "เหตุผล" กำกับไว้ด้วย ไม่ใช่จดแค่ข้อสรุป

Skills (เรียกผู้เชี่ยวชาญ)

ในโรงพยาบาล หมอทุกคนทำตามกฎเดียวกัน (ล้างมือ, บันทึกเวชระเบียน) — นั่นคือ CLAUDE.md/Rules แต่พอมีเคส ผ่าตัดหัวใจ ไม่มีใครเรียกหมอทุกคนในตึกมาช่วย จะเรียกแค่ ศัลยแพทย์หัวใจ ที่เดินเข้ามาพร้อมความรู้เฉพาะทาง ทำเสร็จก็กลับ — หมอทั่วไปไม่ต้องแบกความรู้ผ่าตัดหัวใจไว้ในหัวทุกวัน รู้แค่ว่า "เคสนี้ต้องเรียกใคร" ก็พอ นี่คือหลักการของ Skills

เหมือนแอปในมือถือ — เครื่องไม่โหลดทุกแอปเข้า RAM ตั้งแต่เปิดเครื่อง รู้แค่ว่ามีแอปอะไรติดตั้งไว้ (ไอคอน+ชื่อ) พอแตะเข้าไปแอปค่อยโหลดเต็ม Skills ก็ทำงานแบบเดียวกัน

ก่อนเจาะลึกวิธีสร้าง

Skills ไม่ใช่ของ Claude Code คนเดียว — เป็นมาตรฐานเดียวกันทั้งวงการ

ก่อนหน้านี้ แต่ละค่าย AI coding tool ต่างคนต่างมีวิธี "เพิ่มความสามารถพิเศษ" ให้ผู้ช่วยของตัวเองด้วยชื่อและรูปแบบไม่เหมือนกันเลย Claude Code เองก็เคยเรียกว่า Commands (จะเล่าให้ฟังท้ายสไลด์นี้) พอทุกค่ายต่างคนต่างทำ ผลคือ skill ที่สร้างไว้กับเครื่องมือหนึ่ง เอาไปใช้กับอีกเครื่องมือหนึ่งไม่ได้เลย คนในวงการเลยตกลงร่วมกันตั้ง มาตรฐานเปิด (open standard) ขึ้นมาชื่อว่า Agent Skills ให้ทุกเครื่องมือพูดภาษาเดียวกัน

เครื่องมือที่ adopt มาตรฐานนี้แล้ว

Skill ที่เขียนตามสเปกนี้ พกไปใช้ข้ามเครื่องมือได้ ไม่ต้องเขียนใหม่ทุกที่

  • Cursor
  • GitHub Copilot
  • Gemini CLI
  • Claude Code — พร้อมของเสริมเฉพาะตัวที่ค่ายอื่นยังไม่มี

Claude Code ใช้มาตรฐาน Agent Skills เดียวกันนี้เป็นฐาน แล้วต่อยอดของเฉพาะตัวเพิ่มขึ้นมาอีก 3 อย่าง: คุมการเรียกใช้ได้ละเอียดขึ้น (เปิด/ปิดให้ Claude เรียกเองหรือคนเรียกเท่านั้น), รันใน sub-agent แยกห้องได้ (context: fork ที่จะเห็นในหน้าถัดๆ ไป) และ แทรก context แบบไดนามิกได้ (รันคำสั่งแล้วเอาผลลัพธ์ยัดเข้า instructions ก่อน Claude เริ่มงาน)

กายวิภาคของ Skill

ข้างในโฟลเดอร์ Skill มีอะไรบ้าง

โครงสร้างโฟลเดอร์
.claude/skills/analyze-issue/
├── SKILL.md        (จำเป็น)
├── scripts/        (ทางเลือก — python/bash)
├── references/     (ทางเลือก — เอกสารอ้างอิง)
└── assets/         (ทางเลือก — template, รูป)
ตั้งค่าสำคัญใน SKILL.md
nameกลายเป็น /slash-command (ไม่ใส่ = ใช้ชื่อโฟลเดอร์แทน)
descriptionสิ่งที่ Claude อ่านตอนตัดสินใจใช้ skill — ยิ่งชัดยิ่งเดาถูก
argument-hintโชว์คำแนะนำตอน autocomplete เช่น "issue number" หรือ "file name"
disable-model-invocationtrue = ห้าม Claude เรียกเอง ต้องพิมพ์ /command เท่านั้น
user-invocablefalse = ห้ามคนพิมพ์ /command เรียก เหลือแต่ Claude เรียกเองได้
allowed-toolsจำกัดว่า skill นี้ใช้ tool อะไรได้บ้าง เช่น Read, Grep, Glob เท่านั้น
modelสั่งให้ skill นี้รันด้วยโมเดลเฉพาะ ไม่ใช้โมเดลของเซสชันหลัก
context: forkแยกไปทำงานในห้องต่างหาก ไม่ปนกับบทสนทนาหลัก
agentใช้คู่กับ context: fork — เลือกได้แค่ explore, plan, general-purpose หรือ custom agent ที่สร้างเอง
hooksผูก hook ให้ทำงานตาม lifecycle ของ skill นี้โดยเฉพาะ

ใน SKILL.md ยังใส่ ข้อมูลที่ให้ Claude รู้ล่วงหน้าแบบอัตโนมัติ ได้ — ขึ้นต้นด้วย ! แล้วตามด้วยคำสั่ง bash เช่น !`git remote get-url origin` ผลลัพธ์จะถูกรันและแทรกเข้า context ก่อนที่ Claude จะเริ่มทำงาน — ประหยัด token กว่าปล่อยให้ Claude รันเองทีละคำสั่ง และยังใส่ตัวแปรอย่าง $ARGUMENTS, $1, ${CLAUDE_SESSION_ID} เพื่อรับค่าที่ผู้ใช้พิมพ์ตามหลัง slash command ได้ด้วย

ก่อนสร้างเอง เช็คของสำเร็จรูปก่อน

Claude Code มี Skill ติดเครื่องมาให้แล้วหลายตัว

ก่อนลงมือสร้าง custom skill ทุกครั้ง ควรเช็คก่อนว่า Claude Code มีของสำเร็จรูป (bundled skills) ให้ใช้อยู่แล้วหรือเปล่า — ดูรายการเต็มได้จาก official documentation เสมอ เพราะรายการนี้อัปเดตเพิ่มเรื่อยๆ

/debug ไล่ปัญหาของเซสชันปัจจุบันให้ โดยอ่าน session debug log เอง — ใส่คำอธิบายเพิ่มเติมเข้าไปได้ (optional) เพื่อโฟกัสการวิเคราะห์
/simplify รีวิวไฟล์ที่เพิ่งแก้ไปหา code reuse, quality, efficiency issue แล้ว fix ให้เลย เบื้องหลัง spawn sub-agent รีวิว 3 ตัวพร้อมกัน แล้วรวมผล — ใส่ prompt โฟกัสเฉพาะเรื่องได้ เช่น "focus on memory efficiency"
/batch จัดการงานเป็นชุด (batch operations) แบบสำเร็จรูป
/claude-api และ /loop skill สำเร็จรูปอื่นๆ ที่ Claude Code ให้มาด้วย — รายละเอียดเต็มดูได้ในหน้า official docs

ทั้งหมดนี้เรียกใช้แบบเดียวกับ custom skill ที่เราสร้างเอง — พิมพ์ /simplify ในเซสชันได้เลย ไม่ต้องตั้งค่าอะไรเพิ่ม

Skill ของจริง #1

/analyze-issue — ผู้ช่วยสรุปปัญหาที่มีคนแจ้งเข้ามา

พิมพ์ /analyze-issue 9 เพื่อระบุเลขที่ปัญหา หรือแค่พูดว่า "ช่วยดูปัญหาเลข 5 ให้หน่อย" เฉยๆ ก็ได้ — Claude จะเดาเองว่าควรใช้ผู้ช่วยตัวนี้

สิ่งที่ผู้ช่วยตัวนี้ทำให้แบบอัตโนมัติ

ก่อนเริ่มงาน มันจะไปเตรียมข้อมูลมาให้เองสามอย่าง เราไม่ต้องหามาป้อนเอง

  • รู้ว่ากำลังทำงานอยู่กับโปรเจกต์ไหน ส่วนไหน
  • ไปอ่านรายละเอียดของปัญหาตามเลขที่บอก (หัวข้อ คำอธิบาย ป้ายกำกับ สถานะปัจจุบัน)
  • เข้าไปสำรวจโค้ดในส่วนที่เกี่ยวข้องกับปัญหานั้นจริงๆ

สุดท้ายมันจะสรุปออกมาเป็นรายงานหนึ่งไฟล์ บอกว่า ต้นตอของปัญหาคืออะไร ควรแก้อย่างไร ต้องทดสอบแบบไหน และมีไฟล์ไหนต้องแก้บ้าง — เหมือนได้ "แผนงาน" ก่อนลงมือแก้จริง ไม่ต้องเดาเองตั้งแต่ต้น

Skill ของจริง #2

context: fork — ทำงานแยกห้อง ไม่รก context หลัก

Skill ชื่อ feature-guide ถูกตั้งค่า context: fork และ agent: explore — เมื่อถูกเรียก มันจะไม่ทำงานในบทสนทนาหลัก แต่ไปเปิด ผู้ช่วยแยกตัวไปทำงานอีกห้อง ที่มีแต่คำสั่งของ skill เป็นจุดเริ่มต้น สำรวจโค้ดเบสเสร็จแล้วส่ง "สรุปผล" กลับมาที่บทสนทนาหลักเท่านั้น

บทสนทนาหลัก
"อธิบายฟีเจอร์ของแอดมิน
ให้ฟังหน่อย"
ผู้ช่วยแยกตัว (explore)
ไล่อ่านโค้ดทั้งหมด
เอง ในห้องแยก

ประโยชน์: การไล่อ่านไฟล์เยอะๆ ระหว่างสำรวจโค้ด ไม่ทำให้ context หลักบวม — สิ่งที่กลับเข้ามาคือ คำอธิบายฟีเจอร์แบบมีโครงสร้าง (ทำอะไร, user flow, key files, data flow, state & storage, วิธีต่อขยาย) เท่านั้น

ปลายทางถัดไปของ Skills

ผูก Skill เข้ากับ Sub-agent สร้างผู้เชี่ยวชาญเฉพาะ Domain

ลองนึกภาพแอปธนาคารหรือประกันภัยขนาดใหญ่ ที่มีหลาย domain ในตัวเอง เช่น ลูกค้า (clients), ตรวจจับทุจริต (fraud detection), การชำระเงิน (payments), การรับรองสิทธิ์ (endorsements) — แต่ละ domain สร้างเป็น skill แยกที่มีความรู้เฉพาะทางของตัวเอง แล้วผูกชุด skill เหล่านี้เข้ากับ sub-agent หรือ agent ตัวหนึ่ง

→
agent เดาเองว่า
เป็นคำถาม domain ไหน
→

agent ไม่ต้องแบกความรู้ทุก domain ไว้ในหัวตลอดเวลา รู้แค่ว่าคำถามนี้ควรเรียก skill ไหนมาช่วย — หลักการเดียวกับที่เล่าไปตอนต้น (หมอทั่วไปไม่ต้องรู้เรื่องผ่าตัดหัวใจ แค่รู้ว่าเคสนี้ต้องเรียกใคร) เพียงแต่คราวนี้ขยายจาก "หนึ่ง Claude กับหลาย skill" ไปเป็น "หลาย agent แต่ละตัวถือ skill เฉพาะทางของตัวเอง" — นี่คือจุดเชื่อมต่อไปสู่เรื่อง Agents และ Sub-agents ที่จะเรียนต่อในคอร์สนี้

Commands (ระบบยื่นคำร้องแบบเก่า)

เลิกใช้แล้ว

ก่อนมี Skills, Claude Code มี Commands — ไฟล์ markdown ธรรมดาใน .claude/commands/review.md ที่กลายเป็น /review ได้เลย ไม่มีส่วนตั้งค่าด้านบนไฟล์บังคับ ไม่รองรับไฟล์เสริม และเรียกได้แค่ทางเดียว — คนต้องพิมพ์เท่านั้น Claude เรียกเองไม่ได้

เอกสารทางการของ Claude Code ประกาศไว้ตรงๆ ว่า Commands ถูกรวมเข้าไปเป็นส่วนหนึ่งของ Skills แล้ว ของเดิมที่เคยสร้างไว้ยังใช้ต่อได้ตามปกติ แต่ถ้าตั้งชื่อชนกัน Skill จะชนะเสมอ

ตัวอย่างของจริง: มีคำสั่งชื่อ investigate-change ทำหน้าที่เป็น "นักสืบประวัติไฟล์" — บอกชื่อไฟล์กับตำแหน่งที่สงสัยไป มันจะไล่ดูว่าใครเคยแก้ตรงนี้บ้าง แก้ตอนไหน และทำไมถึงแก้ แล้วสรุปออกมาเป็นรายงานให้อ่านทั้งหมด — ใช้งานได้ดี แต่ต้องพิมพ์เรียกเองทุกครั้ง Claude ไม่สามารถเรียกให้เองได้

เกร็ดเล็กๆ ระหว่างทาง ระหว่างที่ Claude กำลังทำงานยาวๆ อยู่ (ไม่ว่าจะ command, skill หรืองานปกติ) ถ้าอยากถามคำถามแทรกสั้นๆ โดยไม่ขัดจังหวะงานหลัก ใช้คำสั่ง /btw (between) ได้เลย

Commands vs Skills แบบละเอียด

ประเด็นCommands (ของเก่า)Skills (ของปัจจุบัน)
ที่เก็บ.claude/commands/file.md.claude/skills/name/SKILL.md
โครงสร้างไฟล์ markdown เดี่ยวโฟลเดอร์ + ไฟล์เสริม
ใครเรียกได้คนพิมพ์ /command เท่านั้นคนพิมพ์ หรือ Claude เดาแล้วเรียกเอง
ไฟล์เสริมไม่รองรับรองรับ templates, scripts, examples, references
โหลดอัตโนมัติไม่มีทาง — ต้องพิมพ์ / เท่านั้นมี — โหลดเองเมื่อ description ตรงกับงาน
รันใน sub-agentทำไม่ได้ทำได้ผ่าน context: fork
สถานะเลิกใช้แล้ว (แต่ของเดิมยังรันได้)วิธีที่แนะนำให้ใช้ต่อจากนี้

ถ้าตั้งชื่อ command กับ skill ชนกัน Skill จะชนะเสมอ — งานใหม่ทุกชิ้นแนะนำให้เขียนเป็น Skill ตั้งแต่ต้น ส่วน command เก่าที่มีอยู่แล้วยังใช้งานต่อได้ตามปกติ ไม่ต้องรีบย้าย
