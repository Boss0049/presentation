01

Man-in-the-Middle & ทำไมต้อง HTTPS

MITM คืออะไร คำตอบถูก

Attacker แฝงตัวอยู่ระหว่างกลาง Client กับ Server เพื่อดักฟังหรือแก้ไขข้อมูลก่อนถึงปลายทาง โดยทั้งสองฝั่งไม่รู้ตัว

ทำไมใช้ HTTPS ป้องกันได้ คำตอบถูก

HTTPS ทำงานบน TLS ซึ่งไม่ได้ encrypt ข้อมูลอย่างเดียว แต่ทำ authentication ด้วย — ใช้ certificate ให้ client ตรวจสอบว่า server ที่คุยด้วยเป็นตัวจริง ทำให้ attacker ปลอมตัวเป็น server ไม่ได้ง่ายๆ

จุดที่เสริมได้ตอนตอบสัมภาษณ์: HTTPS ป้องกัน MITM ระดับ transport แต่ ไม่ได้ทดแทนเหตุผลที่ยังต้องทำ RSA/AES เข้ารหัสข้อมูลเพิ่มอีกชั้น — เช่น TLS termination ที่ load balancer/proxy, หรือ log ที่ capture request body แบบ plaintext หลัง TLS ถูกถอดแล้ว การเข้ารหัส payload เองเป็นการป้องกัน end-to-end ที่ไม่ผูกกับ transport layer

02

ทำไมต้อง Hybrid Encryption

RSA เข้ารหัสข้อมูลก้อนใหญ่ไม่ได้ คำตอบถูก

RSA มี size limit ผูกกับ key size (เช่น RSA-2048 + OAEP-SHA256 เข้ารหัสได้สูงสุด ~190 bytes) เพราะงั้นถ้ายังต้องใช้ RSA กับ content ก้อนใหญ่ → ต้องทำ Hybrid Encryption

เหตุผลเชิงลึกที่เสริมได้: ไม่ใช่แค่ "เข้ารหัสไม่ได้" แต่ RSA ช้ากว่า AES มาก (asymmetric crypto คำนวณหนักกว่า symmetric หลายเท่า) เพราะงั้นแม้ RSA จะเข้ารหัสก้อนใหญ่ได้ (เช่นด้วยการ chunk) ก็ไม่ควรทำ เพราะ performance แย่ — Hybrid encryption แก้ทั้ง size limit และ performance พร้อมกัน

03

Flow: Client → Server

Client
1
สร้าง AES-256-GCM key แบบ random
2
Encrypt content จริง (ก้อนใหญ่) ด้วย AES-256-GCM
3
เข้ารหัส AES key ด้วย RSA-OAEP (public key)
4
ส่ง payload 4 field ไป server
Server
1
base64-decode ทุก field กลับเป็น binary
2
decrypt AES key ด้วย RSA private key
3
ใช้ AES key + iv + authTag decrypt content จริง

ทั้ง flow นี้ถูกต้องตามหลัก envelope encryption ที่ TLS/PGP ใช้จริง — public key เข้ารหัส, private key ถอด เท่านั้นที่รักษา confidentiality ได้

04

Payload ที่ต้องส่งไป Server

Fieldมาจากไหนทำไมต้องส่ง
encryptedKeyRSA-OAEP เข้ารหัส AES key ด้วย public keyserver ถอดออกมาเป็น AES key ก่อน
ivrandom 12 bytes ทุกครั้งที่ encryptไม่เป็นความลับ แต่ server ต้องใช้ค่าเดียวกันตอน decrypt
ciphertext / encryptedDatacontent เข้ารหัสด้วย AES-256-GCMข้อมูลจริงที่ต้องการปกป้อง
authTag / tagGCM สร้างให้อัตโนมัติตอน encryptยืนยันว่า ciphertext ไม่ถูกแก้ไขระหว่างทาง

ชื่อ field ตั้งเองได้ ไม่มีมาตรฐานบังคับ — ขอแค่ client/server ตกลงชื่อกันให้ตรง ทั้ง 4 field ขาดตัวใดตัวหนึ่งไม่ได้ ไม่งั้น decrypt fail ทันที

05

ทำไมต้อง Base64

ผลลัพธ์จากการเข้ารหัสเป็น binary data (ArrayBuffer/Buffer) แต่ JSON เป็น text format ล้วนๆ ไม่มี type รองรับ binary — ใส่ ArrayBuffer ตรงๆ ใน JSON.stringify() จะได้ค่าว่างหรือพัง

Base64 แปลง binary bytes → string ที่ใช้ตัวอักษร A-Z a-z 0-9 + / เท่านั้น ปลอดภัยสำหรับส่งผ่าน text-based channel ทุกแบบ (JSON body, header, URL) แลกกับขนาดข้อมูลเพิ่ม ~33%

decode ฝั่ง Node.js: Buffer.from(base64String, "base64") · ฝั่ง browser: atob(base64String)

2 จุดที่ต้องแก้ก่อนใช้เป็นโค้ดจริง

Typo ในโน้ต ต้องแก้

// ผิด
aseKey          // → ต้องเป็น aesKey
AES-GDM         // → ต้องเป็น AES-GCM (Galois/Counter Mode)

ถ้าเป็นแค่โน้ตสรุปให้ตัวเองอ่าน ไม่มีผลอะไร แต่ถ้า copy ไปเป็นโค้ดจริง — "AES-GDM" ที่ส่งเข้า crypto.subtle.encrypt() หรือ createCipheriv() จะ throw ทันทีเพราะ algorithm name ไม่มีอยู่จริง

07

GCM คือ Mode ไม่ใช่ Algorithm

ส่วนคืออะไรตัวอย่าง
Algorithm (cipher)สูตรเข้ารหัสจริงAES
Mode of Operationวิธีใช้ cipher กับข้อมูลที่ยาวกว่า 1 block (128-bit)GCM, CBC, CTR, ECB

"AES-256-GCM" = algorithm (AES) + key size (256-bit) + mode (GCM) รวมกัน — GCM ถูกเลือกเพราะมี authTag ในตัว (AEAD) ต่างจาก CBC ที่ต้องเติม HMAC เองไม่งั้นเสี่ยง padding oracle attack

08

ทำไมเลือก AES-256 (ไม่ใช่ 128)

✓Quantum resistance — Grover's algorithm ลด effective security ครึ่งหนึ่ง, AES-128 เหลือ ~64-bit (เสี่ยง) ส่วน AES-256 เหลือ ~128-bit (ยังปลอดภัย)
✓Performance แทบไม่ต่าง — เพิ่มแค่ 10→14 rounds, มี AES-NI hardware ช่วยทั้งคู่
✓Compliance — FIPS/PCI-DSS และงาน fintech/banking มักบังคับ AES-256 เป็น minimum
09

Web Crypto API vs Library (node-forge)

Default: Web Crypto API คำตอบถูก

Native ของ browser — เร็วกว่า (hardware-accelerated), ปลอดภัยกว่า (audited โดย browser vendor, ใช้ CSPRNG จริง), ไม่เพิ่ม bundle size

ใช้ library แทนเมื่อไหร่ คำตอบถูก

•ต้อง support browser เก่ามากที่ไม่มี crypto.subtle
•ต้อง share crypto logic กับฝั่ง Node.js แบบ isomorphic

เลือก node-forge เพราะมีทั้ง AES-GCM และ RSA-OAEP ในตัวเดียว (ไม่ต้อง mix 2 library), community ใหญ่, ผ่านการใช้งานแพร่หลายมานาน, จัดการ PEM/public key format จาก server ได้ตรงไปตรงมา

10

Checklist ก่อนเข้าสัมภาษณ์

✓อธิบาย MITM + เหตุผลที่ HTTPS ป้องกันได้ (certificate → authentication)
✓อธิบายได้ว่า RSA มี size limit จาก key size + ทำไมช้ากว่า AES
✓วาด flow hybrid encryption ได้ทั้ง client และ server โดยไม่ดูโน้ต
✓อธิบาย 4 field ใน payload ได้ว่าแต่ละตัวมาจากไหน ทำไมต้องมี
✓รู้ว่า GCM เป็น mode ไม่ใช่ algorithm, authTag ทำหน้าที่ integrity ไม่ใช่ confidentiality
⚠ระวังพิมพ์ AES-GDM ผิดตอนพูดหรือเขียนกระดาน — ต้องเป็น AES-GCM
✓ตอบได้ว่าทำไมเลือก AES-256 (quantum margin + compliance, ไม่ใช่เพราะ 128 ไม่ปลอดภัย)
