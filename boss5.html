Endpoint ที่ต้องสร้าง

สัญญาที่ brief กำหนด

ทั้งสอง endpoint ตอบกลับด้วย envelope เดียวกัน คู่กับ HTTP status code จริง

POST /get-encrypt-data   { payload: string }              (1-2000 ตัวอักษร, required)
  → { successful, error_code, data: null | { data1, data2 } }

POST /get-decrypt-data   { data1: string, data2: string } (ทั้งคู่ required)
  → { successful, error_code, data: null | { payload } }

แก้ทิศทาง RSA ที่ brief เดิมเขียนผิด

02

Encrypt pipeline

POST /get-encrypt-data
1
random 32-byte key material
2
SHA-256 hash → AES-256 key
3
random 12-byte IV (GCM มาตรฐาน)
4
AES-256-GCM เข้ารหัส payload → ciphertext + authTag
5
แพ็ก {iv, authTag, ciphertext} → JSON → base64 = data2
6
RSA-OAEP-SHA256 เข้ารหัส key material ด้วย public key → base64 = data1
03

Decrypt pipeline (ย้อนกลับทุกขั้นตอน)

POST /get-decrypt-data
1
RSA-decrypt data1 ด้วย private key → key material
2
SHA-256 hash key material → AES-256 key (ตัวเดียวกับตอน encrypt)
3
base64-decode data2 → JSON.parse → {iv, authTag, ciphertext}
4
AES-256-GCM decrypt + verify authTag
5
ได้ payload กลับมาตรงตัวเป๊ะ

Tamper ตรงไหนก็ throw ที่ authTag เสมอ

GCM เป็น authenticated encryption — แก้ ciphertext แม้ 1 bit เดียว setAuthTag() จะ mismatch แล้ว throw ทันที (พิสูจน์แล้วด้วย slice 07 ด้านล่าง)

04

ทำไมเลือกแพ็ก data1/data2 แบบ JSON + base64

รูปแบบจริงของ data2

base64( JSON.stringify({
  iv:         base64(12 bytes),
  authTag:    base64(16 bytes),
  ciphertext: base64(ยาวไม่คงที่ ตาม payload)
}) )

เทียบกับ fixed-length concatenation: ciphertext ยาวไม่คงที่ (payload 1-2000 ตัวอักษร) ทำ length-prefix เพิ่ม complexity โดยไม่ได้อะไร ส่วน JSON+base64 self-describing, debug ง่าย (decode แล้วอ่านเป็น JSON ตรงๆ), ไม่มีปัญหา delimiter ชนกัน

key material 32 byte เล็กกว่า RSA-2048/OAEP-SHA256 max plaintext (190 byte) มาก — ไม่ต้อง chunk data1 เลย

Quirk ของ Node ที่ comment ไว้ในโค้ด

crypto.service.ts

// Buffer.from(str, 'base64') silently drops invalid characters instead of
// throwing, so malformed data1/data2 fails downstream instead (RSA decrypt,
// JSON.parse, or GCM authTag mismatch) — all of which land here.

เพราะงั้น malformed input ไม่ throw ตอน decode แต่จะไปพังที่ RSA decrypt / JSON.parse / GCM authTag แทน — ซึ่ง catch-all เดียวกันจับได้หมดอยู่แล้ว ไม่ใช่บั๊ก

05

Response envelope กับ global exception filter

ไม่มี try/catch format response กระจายอยู่ใน controller

exception ลอยขึ้นไปให้ HttpExceptionFilter ตัวเดียวจับหมด แปลงเป็น envelope เดียวกันเสมอ

ExceptionHTTP Statuserror_code
BadRequestException (จาก ValidationPipe)400VALIDATION_ERROR
DecryptionFailedException (custom)422DECRYPTION_FAILED
อื่นๆ ที่ไม่รู้จัก500 (บังคับเสมอ ไม่เชื่อ status ที่ exception อ้างเอง)INTERNAL_ERROR

จุดเดียวที่มี try/catch จริงคือใน CryptoService.decrypt() — รวบทุก failure (RSA error, JSON.parse error, GCM authTag error) ให้กลายเป็น DecryptionFailedException เดียวก่อนถึง filter เพื่อไม่ให้ผู้โจมตีแยกออกว่า fail ที่ขั้นไหน (ป้องกัน oracle-style attack)

07

Security review — ไม่พบช่องโหว่ high/medium

สิ่งที่เช็คแล้วผ่าน

✓RSA-OAEP + SHA-256 — padding ปลอดภัย ไม่ใช่ PKCS1v1.5 ที่เสี่ยง Bleichenbacher attack
✓IV สุ่มใหม่ + AES key ใหม่ (จาก key material สุ่มใหม่) ทุกครั้งที่ encrypt — ไม่มีความเสี่ยง GCM nonce reuse
✓AuthTag verify จริงผ่าน setAuthTag() — tamper แล้ว throw ถูกต้อง
✓Error ทุกจุด fail ถูกรวบเป็น error_code เดียว — ไม่รั่วว่า fail ที่ RSA/JSON/GCM ขั้นไหน
✓ValidationPipe({ whitelist: true }) ป้องกัน mass-assignment
✓ไม่มี stack trace หรือ internal error message หลุดออกไปใน response

ข้อสังเกต 2 จุด — severity ต่ำ ไม่บล็อกงาน

1. @nestjs/swagger มี transitive dependency js-yaml ที่ npm audit เตือนเป็น high (ReDoS) — ใช้แค่ตอน build-time YAML export ของ Swagger เอง ไม่ถูกเรียกจาก route ไหนเลย ความเสี่ยงจริงต่ำมาก แก้ได้ด้วย npm audit fix --force แต่จะ downgrade เป็น breaking change เลยตัดสินใจเก็บไว้เฉยๆ

2. data1/data2 ใน DecryptRequestDto ไม่มี max length — Express body-parser จำกัดไว้ที่ 100kb เป็นด่านแรกอยู่แล้ว Boss ตัดสินใจไม่ต้องเพิ่ม @MaxLength เพิ่ม (ความเสี่ยงจริงต่ำ ไม่คุ้ม complexity)

หมายเหตุ: skill /security-review เรียกไม่ได้เพราะเช็ค cwd ของ session หลัก (second_brain) ซึ่งไม่ใช่ git repo ของโปรเจกต์นี้ — รีวิวนี้ทำแบบ manual แทน

08

Bugfix หลังส่งงาน: TypeScript ts(2564)

Error: Property 'data1' has no initializer and is not definitely assigned in the constructor

DTO ของ NestJS ไม่เคยถูก new ขึ้นมาพร้อม field ครบผ่าน constructor — class-validator/class-transformer เป็นคนเติมค่าให้ตอน runtime (จาก request body) ดังนั้น field ที่ declare แบบ data1: string; เฉยๆ TypeScript จะมองว่า "อาจไม่เคยถูก assign เลย" ภายใต้ strict mode

// ก่อนแก้ — TS มองว่าไม่ชัวร์ว่าถูก assign
export class DecryptRequestDto {
  @IsNotEmpty()
  @IsString()
  data1: string;
}

// หลังแก้ — definite assignment assertion (!) บอก TS ว่ารู้แน่นอนว่าจะมีค่า
export class DecryptRequestDto {
  @IsNotEmpty()
  @IsString()
  data1!: string;
}

แก้ทุก DTO field ในโปรเจกต์ให้ตรงกันหมด (encrypt/decrypt request + response DTOs) เป็น pattern มาตรฐานของ NestJS พร้อมกันนั้นก็เจอ ApiErrorResponseDto ที่สร้างไว้ตอน slice แรกๆ แต่ไม่เคยถูก import ใช้จริงเลย — ลบทิ้งไปด้วยแทนที่จะแปะ ! ให้โค้ดที่ไม่มีใครใช้

ยืนยันแล้วว่า npx tsc --noEmit ผ่านทั้งแบบปกติและแบบ --strict, npm run build, npm run lint, และ e2e ทั้ง 16 test ยังผ่านครบหลังแก้

Code walkthrough — อธิบายทุกไฟล์ตามลำดับที่ request ไหลผ่าน

1. Bootstrap — src/main.ts

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  setupApp(app);
  await app.listen(process.env.PORT ?? 3000);
}
void bootstrap();

สร้าง Nest app จาก AppModule แล้วเรียก setupApp(app) ก่อน listen — แยกฟังก์ชันนี้ออกมาต่างหากเพราะ e2e test ทุกไฟล์ต้องเรียกอันเดียวกันนี้ ตอน bootstrap TestingModule ไม่งั้น test จะไม่มี validation/filter/swagger เหมือน production จริง void bootstrap() คือบอก ESLint ว่าตั้งใจไม่ await promise นี้ (มันเป็น entry point ไม่มีใคร await มันอยู่แล้ว)

2. src/setup-app.ts — global wiring

export function setupApp(app: INestApplication) {
  app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }));
  app.useGlobalFilters(new HttpExceptionFilter());
  setupSwagger(app);
}

3 บรรทัดนี้คือ "ระบบประสาทส่วนกลาง" ของทั้ง API:

ValidationPipe({ whitelist: true, transform: true }) — เช็ค DTO validation อัตโนมัติทุก request ก่อนเข้า controller เลย whitelist ตัด field แปลกปลอมที่ไม่ได้ประกาศใน DTO ทิ้ง (กัน mass-assignment) transform แปลง plain JSON object ให้กลายเป็น instance ของ DTO class จริงๆ — ถ้าไม่ transform, @IsString() จะไม่รู้จัก field เพราะ request body ที่มาจาก Express เป็นแค่ plain object เฉยๆ

useGlobalFilters(new HttpExceptionFilter()) — exception ทุกตัวที่ throw ในแอปวิ่งมาจบที่ filter ตัวนี้ที่เดียว (อธิบายละเอียดในข้อ 11)

setupSwagger(app) — ผูก Swagger เข้ากับ app instance เดียวกัน

3. src/swagger.ts

const document = SwaggerModule.createDocument(app, config);
SwaggerModule.setup('api-docs', app, document);

สแกน decorators (@ApiTags, @ApiOperation, @ApiProperty ฯลฯ) จากทุก controller/DTO ที่ registered ใน app แล้ว generate OpenAPI spec ขึ้นมาสด ๆ เสิร์ฟที่ /api-docs (หน้า UI) และ /api-docs-json (raw spec ที่ test slice 10 เอาไป assert ว่ามี path/schema ครบ)

4. Config — app.module.ts + env.validation.ts

ConfigModule.forRoot({ isGlobal: true, validationSchema: envValidationSchema })

isGlobal: true ทำให้ ConfigService inject ที่ไหนก็ได้ในแอปโดยไม่ต้อง import ConfigModule ซ้ำในทุกโมดูล validationSchema คือ Joi object ที่บังคับว่า .env ต้องมี RSA_PUBLIC_KEY/RSA_PRIVATE_KEY — ถ้าไม่มี แอปจะไม่ยอม start เลย ตั้งแต่ตอน boot (fail fast ดีกว่าไปพังตอนมี encrypt request แรกเข้ามา)

5. DI wiring — crypto.module.ts

@Module({
  controllers: [CryptoController],
  providers: [RsaService, AesService, CryptoService],
})
export class CryptoModule {}

ประกาศว่าโมดูลนี้มี controller ตัวเดียว (CryptoController) และ provider (service) 3 ตัว — Nest จะสร้าง instance ของทั้ง 3 ตัวนี้แบบ singleton แล้ว inject ผ่าน constructor ให้เองตาม dependency graph (CryptoController ต้องการ CryptoService, CryptoService ต้องการ RsaService + AesService)

6. HTTP layer — crypto.controller.ts

@Post('get-encrypt-data')
@HttpCode(HttpStatus.OK)
encrypt(@Body() dto: EncryptRequestDto) {
  const data = this.cryptoService.encrypt(dto.payload);
  return { successful: true, error_code: '', data };
}

สังเกตว่า controller ไม่มี try/catch เลย — ถ้า cryptoService.encrypt()/.decrypt() throw อะไรออกมา มันจะลอยตรงไปหา HttpExceptionFilter ทันที เป็น design ที่ตั้งใจ ไม่ใช่ลืมเขียน error handling

@HttpCode(HttpStatus.OK) ต้องใส่เพราะ Nest default ของ @Post คือ 201 Created ซึ่งไม่ตรงกับ spec ที่ต้องการ 200 ทั้งสอง endpoint ตอน success

dto: EncryptRequestDto ผ่านการ validate โดย global pipe ไปแล้วตั้งแต่ก่อนเข้า method นี้ — ถ้า dto.payload ไม่ผ่านเงื่อนไขใน DTO, method นี้จะไม่ถูกเรียกเลยด้วยซ้ำ (pipe คืน 400 ไปก่อน)

7. DTOs — validation + Swagger schema ในตัวเดียว

export class DecryptRequestDto {
  @ApiProperty()
  @IsNotEmpty()
  @IsString()
  data1!: string;   // definite assignment assertion — ดูข้อ 08 ด้านบน

  @ApiProperty()
  @IsNotEmpty()
  @IsString()
  data2!: string;
}

DTO class เดียวทำหน้าที่ 2 อย่างพร้อมกัน: @IsNotEmpty()/@IsString()/@Length() จาก class-validator ให้ ValidationPipe เช็ค request จริง ส่วน @ApiProperty() จาก @nestjs/swagger ให้ Swagger generate schema — เขียนที่เดียว ได้ทั้ง validation และ documentation ตรงกันเป๊ะ ไม่มีวันเพี้ยนจากกัน

มี 4 ไฟล์ทำหน้าที่นี้: encrypt-request.dto.ts, decrypt-request.dto.ts (request), encrypt-response.dto.ts, decrypt-response.dto.ts (response — ใช้แค่กับ @ApiResponse() ให้ Swagger รู้ shape ตอนตอบกลับ ไม่ได้ผ่าน validation เพราะเป็นข้อมูลขาออก)

8. ตัวประสานงาน — crypto.service.ts

encrypt(payload: string) {
  const keyMaterial = this.aesService.generateKeyMaterial();
  const data2 = this.aesService.encrypt(payload, keyMaterial);
  const data1 = this.rsaService.encrypt(keyMaterial).toString('base64');
  return { data1, data2 };
}

decrypt(data1: string, data2: string) {
  try {
    const keyMaterial = this.rsaService.decrypt(Buffer.from(data1, 'base64'));
    const payload = this.aesService.decrypt(data2, keyMaterial);
    return { payload };
  } catch {
    throw new DecryptionFailedException();
  }
}

ตัวนี้ไม่รู้จัก crypto algorithm เลยสักตัว รู้แค่ลำดับ "เรียก AES ก่อนแล้วเอา key material ไปเข้า RSA" — แยก concern ชัดเจน: RsaService/AesService ไม่รู้จักกันเอง ไม่มีใครอ้างอิงอีกฝั่งเลย ทำให้ทดสอบ/แก้แยกกันได้อิสระ

try/catch ที่นี่คือจุดเดียวในทั้งโปรเจกต์ที่ดัก error ของ crypto logic เอง — ไม่สนว่า fail เพราะอะไร (RSA decrypt พัง, JSON.parse พัง, หรือ GCM authTag mismatch) โยนเป็น DecryptionFailedException เดียวกันหมด เพื่อไม่ให้ผู้โจมตีแยกได้ว่า fail ที่ขั้นไหน (ป้องกัน oracle-style attack ตามที่เขียนไว้ใน section 07)

9. rsa.service.ts — RSA-OAEP

constructor(configService: ConfigService) {
  this.publicKey = configService
    .getOrThrow<string>('RSA_PUBLIC_KEY')
    .replace(/\\n/g, '\n');   // .env เก็บ \n เป็น literal 2 ตัวอักษร ต้องแปลงกลับเป็น newline จริง
  // ... privateKey เหมือนกัน
}

encrypt(data: Buffer): Buffer {
  return publicEncrypt(
    { key: this.publicKey, padding: constants.RSA_PKCS1_OAEP_PADDING, oaepHash: 'sha256' },
    data,
  );
}

getOrThrow() แทน get() เฉยๆ — ถ้า key หายไปจาก config จะ throw ทันทีตอน constructor รัน (ตอน app boot) ไม่ใช่ไปพังแบบเงียบๆ ตอนมี request เข้ามาแล้ว

key อ่านจาก ConfigService แค่ครั้งเดียวตอน constructor แล้ว cache ไว้ในตัวแปร instance (private readonly) — ไม่ parse ซ้ำทุก request

RSA_PKCS1_OAEP_PADDING + oaepHash: 'sha256' คือ padding ที่ตั้งใจเลือก (ไม่ใช่ default) เพราะ PKCS1v1.5 padding แบบเก่ามีช่องโหว่ Bleichenbacher attack ที่รู้จักกันดี ส่วน encrypt()/decrypt() ใช้ key คนละดอกกัน (public/private) ตามที่แก้จาก brief เดิมใน section 01

10. aes.service.ts — AES-256-GCM + pack/unpack

encrypt(payload: string, keyMaterial: Buffer): string {
  const key = this.deriveKey(keyMaterial);        // sha256(keyMaterial) → 32 byte พอดีสำหรับ AES-256
  const iv = randomBytes(IV_LENGTH);               // 12 byte สุ่มใหม่ทุกครั้ง
  const cipher = createCipheriv('aes-256-gcm', key, iv);
  const ciphertext = Buffer.concat([cipher.update(payload, 'utf8'), cipher.final()]);
  const authTag = cipher.getAuthTag();             // GCM คำนวณ tag ยืนยันความถูกต้องให้อัตโนมัติ

  const packed = { iv: ..., authTag: ..., ciphertext: ... };  // แต่ละตัว base64 แยกกัน
  return Buffer.from(JSON.stringify(packed)).toString('base64');
}

deriveKey() เป็น private method — ใช้ภายในคลาสนี้เท่านั้น ไม่มีใครข้างนอกต้องรู้ว่า AES key มาจากการ hash key material ด้วย SHA-256

ทำไมต้อง hash ก่อน: keyMaterial ที่สุ่มมาคือ randomBytes(32) ซึ่งจริงๆ ก็ 32 byte พอดีสำหรับ AES-256 อยู่แล้ว แต่ hash ผ่าน SHA-256 อีกชั้นเป็นการยืนยัน (defensive) ว่าได้ key length ที่ถูกต้องเป๊ะเสมอไม่ว่าจะเปลี่ยนวิธีสุ่มยังไงในอนาคต

decrypt() ทำย้อนกลับ: unpack JSON → setAuthTag() → decipher.update()+final() — ถ้า ciphertext หรือ authTag ถูกแก้แม้ 1 bit, final() จะ throw ทันที (นี่คือกลไกที่ทำให้ test slice 07 "tamper data2" ได้ผลลัพธ์ 422 จริง)

11. Error handling 3 ไฟล์ที่ทำงานร่วมกัน

// error-code.enum.ts — string constant กันพิมพ์ผิด
export enum ErrorCode {
  VALIDATION_ERROR = 'VALIDATION_ERROR',
  DECRYPTION_FAILED = 'DECRYPTION_FAILED',
  INTERNAL_ERROR = 'INTERNAL_ERROR',
}

// decryption-failed.exception.ts — HttpException ชนิดใหม่ที่ Nest เข้าใจเอง
export class DecryptionFailedException extends HttpException {
  constructor() { super('Decryption failed', HttpStatus.UNPROCESSABLE_ENTITY); }
}

// http-exception.filter.ts — จุดรวมทุกอย่าง (@Catch() ไม่ใส่ type = จับทุก exception)
@Catch()
export class HttpExceptionFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost) {
    // if/else if/else ไล่เช็คชนิด exception → เลือก status + error_code
    // ตอบกลับ { successful: false, error_code, data: null } เสมอ 3 field นี้เท่านั้น
  }
}

@Catch() ไม่ระบุ type ในวงเล็บ = จับ exception ทุกชนิด ที่ throw ในแอป ไม่ใช่แค่ HttpException — สำคัญเพราะ error ที่ไม่คาดคิด (เช่น bug ที่ยังไม่รู้) ก็ต้องถูกแปลงเป็น envelope เดียวกัน ไม่ใช่ปล่อยให้ Express ตอบ HTML error page แบบ default

ลำดับการเช็คใน if/else if/else สำคัญ: เช็ค BadRequestException (มาจาก validation) ก่อน, แล้วค่อย DecryptionFailedException (custom), อะไรที่ไม่เข้าเงื่อนไขไหนเลยบังคับเป็น 500/INTERNAL_ERROR เสมอ — ไม่เชื่อ status ที่ exception แปลกๆ อ้างเอง กันไม่ให้ error ที่ไม่รู้จักหลุดไปเป็น status code ที่ดูเหมือนปลอดภัยกว่าความเป็นจริง
