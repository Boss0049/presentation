01

Webhook idempotency

หลักการ

Idempotent write — ประมวลผล event เดียวกันซ้ำกี่ครั้งก็ต้องได้ state เดิม ไม่ใช่ข้อมูลซ้อนกันเพิ่มขึ้นเรื่อยๆ

สาเหตุ

LINE ส่ง webhook แบบ at-least-once (อาจส่งซ้ำได้) ตอนแรกไม่มี dedup อะไรเลย — ถ้า LINE retry ข้อความเดิมจะถูก insert ซ้ำเข้า DB

-- partial unique index: กัน insert ซ้ำเฉพาะแถวที่มี line_message_id จริง (inbound เท่านั้น)
CREATE UNIQUE INDEX uq_messages_line_message_id
  ON messages (line_message_id) WHERE line_message_id IS NOT NULL;

-- insertMessage ใช้ ON CONFLICT DO NOTHING แล้ว return null ถ้าเจอซ้ำ
-- webhook route: ถ้า insert คืน null = ซ้ำ ข้าม touchConversation ไปเลย
Pro
  • DB constraint การันตี 100% ไม่มีทาง insert ซ้ำ แม้ concurrent request ก็ปลอดภัย (ไม่ใช่ check-then-insert ที่มี race)
  • ต้นทุนต่ำมาก — แค่เพิ่ม index ไม่ต้องเขียน logic เช็คเองในแอป
Con
  • ถ้ามีข้อมูลซ้ำอยู่ก่อนแล้วใน DB จริง migration จะ fail ต้อง clean data ก่อน
  • schema.sql รันเป็น transaction เดียวทั้งไฟล์ — ถ้า statement ไหนพัง ทุก statement ใน run นั้นถูก rollback หมด (ความเสี่ยงเชิงโครงสร้างเพราะยังไม่มี migration tool)
ศัพท์เทคนิค
Idempotent write
การเขียนข้อมูลที่ทำซ้ำกี่ครั้งก็ได้ผลลัพธ์เดิมเป๊ะ — ไม่ใช่ยิ่งทำยิ่งข้อมูลเพิ่ม
At-least-once delivery
รูปแบบการส่ง event ของ LINE ที่การันตีว่าถึงปลายทางอย่างน้อย 1 ครั้ง แต่ยอมให้ส่งซ้ำได้ (ตรงข้ามกับ exactly-once ที่การันตีว่าส่งครั้งเดียวเป๊ะ)
Partial unique index
Index ของ DB ที่บังคับห้ามค่าซ้ำ แต่บังคับ "เฉพาะแถวที่เข้าเงื่อนไข" ที่ระบุ (ในที่นี้เฉพาะแถวที่ line_message_id ไม่เป็น null)
ON CONFLICT DO NOTHING
คำสั่ง SQL บอกว่า ถ้า insert ชน constraint (เช่นค่าซ้ำ) ให้ข้ามเงียบๆ ไม่ throw error
Race condition
บั๊กที่เกิดจากหลาย request/process ทำงานแข่งกันพร้อมกัน แล้วผลลัพธ์ขึ้นกับ timing ที่ควบคุมไม่ได้
02

Defensive send path

หลักการ

แยก failure ที่ "retry ได้อย่างปลอดภัย" ออกจาก failure ที่ "retry แล้วอันตราย" — เพราะ side effect ภายนอก (ส่งไป LINE จริง) กับ side effect ภายใน (เขียน DB) เป็นคนละ transaction boundary ที่ล้มเหลวได้อิสระจากกัน

สาเหตุ

โค้ดเดิม: ถ้า push LINE สำเร็จแต่ save DB fail จะได้ error 502 เหมือนกับตอน push fail จริง — ฝั่งเรียกไม่รู้ว่าข้อความไปถึงลูกค้าจริงแล้วหรือยัง เสี่ยงกดส่งซ้ำแล้วลูกค้าได้ข้อความซ้ำจริง

// แยก try/catch เป็น 2 ก้อน + คั่นด้วย field แยกความหมาย
try { await pushText(userId, text); }
catch (err) { return 502; }                    // ไม่เคยส่งถึงลูกค้า → retry ได้

try { insertMessage(...); touchConversation(...); }
catch { return { delivered: true }, 500; }      // ถึงลูกค้าแล้ว → ห้าม retry
Pro
  • กันการส่งข้อความซ้ำไปหาลูกค้าจริง — ความเสี่ยงระดับ user-facing ที่ร้ายแรงสุดในบรรดาบั๊กที่เจอทั้งหมด
  • เพิ่ม cap 5,000 ตัวอักษรตรงกับ limit จริงของ LINE ดักได้ก่อนเสียโควตายิง push
Con
  • โค้ดซับซ้อนขึ้นเล็กน้อย (2 try/catch แทน 1)
  • เคส "delivered แต่ save ไม่ได้" ยังไม่มีทาง "save ใหม่อย่างเดียว" (ต้องทำ endpoint แยกถ้าจะแก้ต่อ — ตอนนี้ scope แค่ dismiss ทิ้ง)
ศัพท์เทคนิค
Retryable vs non-retryable failure
แยก error ที่ "ลองใหม่ได้อย่างปลอดภัย" (ผลจริงยังไม่เกิด) ออกจาก error ที่ "ห้ามลองใหม่" (ผลจริงเกิดไปแล้ว ลองใหม่จะซ้ำ)
Side effect
ผลที่เกิดขึ้นจริงในโลกภายนอกโค้ด เช่น ส่งข้อความถึงลูกค้าจริง หรือเขียนแถวลง DB จริง
Transaction boundary
ขอบเขตของงานที่ "สำเร็จหรือล้มเหลวไปด้วยกันทั้งหมด" — ในเคสนี้ push ไป LINE กับ save DB เป็นคนละขอบเขต ล้มเหลวอิสระจากกันได้
HTTP 502 / 500
502 = server เราไปเรียก service ภายนอก (LINE) แล้วมันพัง; 500 = server เราเองพังตอนทำงานภายใน
03

Realtime ผ่าน SSE (polling ห่อ SSE)

หลักการ

เลือกสถาปัตยกรรมที่ง่ายที่สุดที่ยังทำงานได้จริงภายใต้ข้อจำกัดของ platform — ไม่จำเป็นต้องใช้ infra หนัก (LISTEN/NOTIFY, Redis pub-sub, paid service) ถ้าสเกลงานไม่ต้องการขนาดนั้น

สาเหตุ

Poll 3 วิเดิมรู้สึกช้า อยาก "realtime" แต่ Vercel serverless function มี maxDuration จำกัด ทำให้ WebSocket/SSE แบบเปิดค้างยาวๆ ทำไม่ได้ตรงๆ

// server-side poll DB ทุก 500ms ห่อด้วย SSE stream ที่ปิดตัวเองทุก ~50 วิ
// EventSource ของ browser reconnect ให้อัตโนมัติ — ไม่ต้องเขียน retry logic เอง
Pro
  • ไม่ต้องเพิ่ม infra ใหม่เลย (ไม่มี Ably, ไม่มี Redis) — ประหยัดกว่า line-webchat-main ที่ต้องพึ่ง Ably (มีค่าใช้จ่าย)
  • เร็วขึ้นจริงเทียบ poll 3 วิเดิม และ EventSource reconnect ได้ฟรีจาก browser
Con
  • ยังเป็น polling อยู่ดี — DB ถูก query ทุก 500ms ต่อ 1 tab ที่เปิดอยู่ (ถี่กว่า poll 3 วิเดิม ไม่ใช่น้อยกว่า)
  • reconnect ทุก ~50 วิมี overhead เล็กน้อย และถ้า deploy plan ที่ maxDuration สั้นกว่าที่คิด (เช่น Hobby ไม่เปิด Fluid Compute) จะ reconnect ถี่กว่าที่ออกแบบไว้
ศัพท์เทคนิค
SSE (Server-Sent Events)
เทคโนโลยีให้ server ส่งข้อมูลไปหา browser ต่อเนื่องผ่าน connection เดียว เป็นทางเดียว (server → client เท่านั้น)
WebSocket
การเชื่อมต่อสองทาง (client ↔ server) แบบเปิดค้างไว้ตลอด ต่างจาก SSE ที่ทางเดียวและเปิดง่ายกว่าบน infra จำกัด
Polling
Browser ถามซ้ำๆเป็นช่วงเวลา (เช่นทุก 3 วินาที) ว่ามีข้อมูลใหม่ไหม — วิธีที่ง่ายที่สุดแต่ไม่ real-time จริง
Serverless maxDuration
ข้อจำกัดของ Vercel ว่า function หนึ่งรันได้นานสุดกี่วินาทีก่อนถูกตัดตาย ทำให้เปิด connection ค้างยาวๆแบบ WebSocket ตรงๆทำไม่ได้
EventSource
API ที่ built-in มากับ browser สำหรับเชื่อมต่อ SSE endpoint และ reconnect ให้อัตโนมัติเวลาสายหลุด โดยไม่ต้องเขียน retry logic เอง
04

Image proxy endpoint

หลักการ

ห้ามให้ secret (channel access token) หลุดไปถึง browser — ทุกการเรียก external API ที่ต้องใช้ secret ต้องอยู่หลัง backend ของเราเอง (server-side proxy pattern)

สาเหตุ

LINE Content API ต้องใช้ channel access token ใน header ใช้เป็น <img src> ตรงๆ จาก browser ไม่ได้ — เดิมรูปภาพเข้ามาโชว์แค่ [Unsupported: image]

Pro
  • token ไม่มีทางหลุดไปฝั่ง client เลย
  • proxy เช็คก่อนว่า lineMessageId มีอยู่จริงในระบบและเป็น type image ก่อนยอม fetch — กันไม่ให้กลายเป็น open relay ที่ใครก็เอา token เราไปใช้ยิง ID มั่วๆ ได้
Con
  • ไม่มี cache ฝั่ง server — เปิดรูปซ้ำ (คนละ browser/หมด cache) ต้องยิงไป LINE ใหม่ทุกครั้ง
  • ใช้ unoptimized บน next/image เลยไม่ได้ resize/บีบอัดรูปให้เบาลง
ศัพท์เทคนิค
Server-side proxy pattern
ให้ backend ของเราเป็นตัวกลางเรียก API ภายนอกแทน browser เพื่อไม่ให้ secret หลุดไปฝั่ง client
Channel access token
กุญแจลับที่ใช้ยืนยันตัวกับ LINE API — ถ้าหลุดไปฝั่ง client ใครก็เอาไปใช้แทนเราได้ทันที
Open relay
ระบบที่ยอม forward request ให้ใครก็ได้โดยไม่เช็คสิทธิ์ กลายเป็นช่องให้คนอื่นแอบใช้ token/resource ของเราฟรี
05

Mark-as-read sync ไป LINE

หลักการ

เช็คเอกสาร API จริงก่อนเขียนโค้ด ไม่เดาจากความเข้าใจเอง — ระหว่างทางเคยเข้าใจผิดว่า feature นี้มีผลแค่ในเครื่องมือแอดมินของ LINE เอง แต่พอไปอ่านเอกสารจริงพบว่าไม่ใช่ ต้องแก้คำอธิบายกลับ

สาเหตุ

อยากให้ "อ่านแล้ว" ขึ้นในแอป LINE ฝั่งลูกค้าเหมือนแชทคนทั่วไป ซึ่งไม่เกิดเองกับ Official Account ต้องเรียก API บอก LINE เอง

// capture markAsReadToken จาก webhook event ตอนข้อความเข้ามา (เก็บทีหลังไม่ได้)
// POST /v2/bot/chat/markAsRead — ยิงแบบ best-effort ไม่ block response หลัก
Pro
  • ลูกค้าเห็น "อ่านแล้ว" จริงเหมือนแชทคนทั่วไป — ฟีเจอร์ที่คู่แข่งอ้างอิงบางตัวก็ไม่มี
  • fail แบบ silent ไม่ทำให้ request หลัก (mark read ในระบบเรา) พังไปด้วย — DB ของเราเป็น source of truth เสมอ
Con
  • มี precondition นอกเหนือการควบคุมของโค้ด — ต้องเปิด "Chat" ใน LINE Official Account Manager ก่อน ถ้าลืมเปิดจะดูเหมือนฟีเจอร์ไม่ทำงาน
  • ถ้า sync ไป LINE fail จะแค่ log เงียบๆ — ต้องเปิด log เองถึงจะรู้ว่ามีปัญหา
ศัพท์เทคนิค
Best-effort
พยายามทำแต่ถ้าล้มเหลวก็ไม่ทำให้งานหลักพังตาม — ยอมรับล่วงหน้าว่าอาจไม่สำเร็จ
Source of truth
ข้อมูลชุดที่ถือว่า "ถูกต้องที่สุด" เวลามีหลายที่เก็บข้อมูลเดียวกันแล้วขัดแย้งกัน (ในเคสนี้คือ DB ของเราเอง ไม่ใช่ LINE)
06

Optimistic UI + แยก retry/dismiss

หลักการ

Optimistic UI ช่วยให้รู้สึกไวขึ้น แต่ต้อง reconcile กับความจริงจาก server ให้ถูกต้อง — และปุ่ม "retry" ต้องไม่มีวันปล่อยให้ action ที่เกิดขึ้นจริงแล้วถูกทำซ้ำ

สาเหตุ

เดิมไม่มี optimistic update เลย composer ค้างรอ round-trip เต็มๆ ก่อนเคลียร์ช่องพิมพ์ ไม่มีปุ่ม retry ต้องพิมพ์ใหม่เอง

// onMutate: ใส่ bubble ปลอม (id ติดลบ) ทันที status "pending"
// onError: เช็ค flag "delivered" จาก server แยก status "failed" (retry ได้) vs "delivered_unconfirmed" (ห้าม retry มีแต่ปิด)
Pro
  • รู้สึกไวขึ้นทันที ไม่ต้องรอ network
  • กันการส่งซ้ำจริงในเคสหายากที่สุด (push สำเร็จแต่ save fail) ได้ถูกต้อง — ตรงกับ UX แชทสมัยใหม่
Con
  • state machine ซับซ้อนขึ้น (3 สถานะต้องจัดการ: pending / failed / delivered_unconfirmed)
  • ต้องออกแบบร่วมกับ SSE merge logic อย่างระวัง ไม่งั้นเกิดบั๊กคนละแบบ (ดูข้อ 07 กับปัญหา bubble หายที่เคยเจอ)
ศัพท์เทคนิค
Optimistic UI
อัปเดตหน้าจอ "ล่วงหน้า" ทันทีที่ user กดทำอะไร โดยไม่รอผลจริงจาก server ก่อน — สมมติไว้ก่อนว่าจะสำเร็จ
Reconcile
กระบวนการเทียบ/ปรับ state ที่เดาไว้ล่วงหน้า (optimistic) ให้ตรงกับความจริงที่ server ตอบกลับมา
State machine
การกำหนดสถานะที่เป็นไปได้ทั้งหมดของสิ่งหนึ่งอย่างชัดเจน (ที่นี่คือ pending / failed / delivered_unconfirmed) พร้อมกฎว่าเปลี่ยนจากสถานะไหนไปไหนได้บ้าง
onMutate / onError
Hook ของ TanStack Query — onMutate รันก่อนยิง request จริง (ใส่ optimistic data), onError รันตอน request fail เพื่อ rollback/จัดการ state
07

แก้ bubble กระพริบ (atomic swap)

หลักการ

การเปลี่ยน state ต้องเป็น atomic — ห้ามลบของเก่าทิ้งแล้ว "หวัง" ว่าของใหม่จะมาแทนแบบ async โดยไม่มีอะไรค้ำระหว่างนั้น

สาเหตุ

โค้ดเดิม: ตอนส่งสำเร็จ ลบ bubble ปลอมทิ้งทันที แล้วค่อยยิง fetch ข้อมูลจริงทีหลัง (2 ขั้นตอนแยกกัน มีช่องว่างระหว่างกลาง) — ข้อความหายไปแวบหนึ่งก่อนโผล่กลับมา สังเกตเห็นชัดขึ้นหลังจากที่ composer เร็วขึ้นแล้ว (ข้อ 08)

// server คืนข้อความจริงที่เพิ่งบันทึกกลับมาด้วย
// client สลับ (map) bubble ปลอมเป็นของจริง ในการเขียน cache "ครั้งเดียว" ไม่มีช่องว่าง
Pro
  • หายกระพริบสนิท ไม่มี delay เพิ่ม
  • ประหยัดกว่าเดิมด้วยซ้ำ — ตัด fetch เพิ่มออกไปในเคสปกติ
Con
  • client ผูกกับ shape ของ response มากขึ้น (ต้องมี field message) — มี fallback รองรับกรณีไม่มีแต่แทบไม่ถูกใช้จริง
ศัพท์เทคนิค
Atomic
การกระทำที่เกิดขึ้น "ทั้งหมดในจังหวะเดียว" ไม่มีช่วงกึ่งสำเร็จให้คนอื่นเห็นระหว่างกลาง (all-or-nothing ในทีเดียว)
Cache write
การเขียนข้อมูลลง client-side cache (ในที่นี้คือ cache ของ TanStack Query) โดยตรง แทนการยิง fetch ใหม่
08

Composer เคลียร์ทันที (ไม่รอ round-trip)

หลักการ

อย่าผูก feedback ของ UI ไว้กับ network round-trip ถ้ามี optimistic state ที่อื่นให้ feedback อยู่แล้ว — สอง mechanism ที่ทำหน้าที่ซ้ำกันจะขัดกันเอง

สาเหตุ

ตอนทำ optimistic UI (ข้อ 06) ลืมย้อนกลับมาแก้ composer เดิม — composer ยังรอ mutation จบทั้งก้อนก่อนเคลียร์ช่องพิมพ์/ปลดล็อก input ทำให้ "รู้สึกช้า" ทั้งที่ bubble ขึ้นเร็วแล้วจริงๆ

Pro
  • ช่องพิมพ์รู้สึกไวทันที ไม่ขึ้นกับ network latency เลย
  • ลบ error banner ซ้ำซ้อนใน composer ออก (สถานะทั้งหมดไปอยู่ที่ bubble ที่เดียว)
Con
  • ไม่มีจริง — เป็นแค่การแก้ให้ตรงกับดีไซน์ optimistic UI ที่ควรทำพร้อมกันตั้งแต่แรก
ศัพท์เทคนิค
Round-trip
เวลาที่ request เดินทางไปเซิร์ฟเวอร์แล้วตอบกลับมาครบรอบ — ถ้า UI รอ round-trip ก่อนตอบสนอง จะรู้สึกช้าตาม network latency
09

Loading component (แยกจาก duplicate)

หลักการ

DRY — ดึง UI ที่ซ้ำกันออกมาเป็น component กลาง แทนที่จะ copy-paste markup เดิมซ้ำสองจุด

สาเหตุ

มี loading state 2 จุด (ConversationList, MessageThread) เป็นข้อความเฉยๆ ไม่มี spinner เลย

Pro
  • UI สม่ำเสมอ โค้ดซ้ำน้อยลง
  • ได้ spinner จริงเพิ่มมาด้วย ไม่ใช่แค่ refactor เฉยๆ
Con
  • แทบไม่มี — งานเล็ก ความเสี่ยงต่ำ
ศัพท์เทคนิค
DRY (Don't Repeat Yourself)
หลักการเขียนโค้ดไม่ให้ซ้ำ — ถ้ามี logic/UI เดิมซ้ำกันหลายที่ ให้ดึงออกมาเป็นจุดเดียวแล้วเรียกใช้ร่วมกัน
10

Date separator (จัดกลุ่มรายวัน)

หลักการ

ลด cognitive load ของ list ที่ scroll ยาวๆ ด้วยการจัดกลุ่ม — pattern มาตรฐานที่แชทเกือบทุกแอปใช้

สาเหตุ

ไม่มี indicator บอกว่าข้อความไหนเป็นของวันไหนเลย

Pro
  • ตรงกับความคุ้นเคยของผู้ใช้จากแอปแชททั่วไป
  • เขียนเป็น pure function (isNewDay, formatDateLabel) เทสได้ตรงๆ ไม่ต้องพึ่ง React
Con
  • ใช้ timezone ท้องถิ่นของ browser (ถูกต้องแล้วสำหรับคนอ่าน) แต่ทำให้เขียนเทสยากขึ้น — เจอบั๊กจริงตอนเขียนเทสเพราะเครื่องรันอยู่ timezone Bangkok (+7) แล้ว timestamp ใกล้เที่ยงคืน UTC ข้ามวันโดยไม่ตั้งใจ
ศัพท์เทคนิค
Pure function
ฟังก์ชันที่ input เดียวกันได้ output เดียวกันเสมอ ไม่มี side effect ไม่พึ่ง state ภายนอก — เทสง่ายเพราะไม่ต้องพึ่งอะไรรอบข้าง
Cognitive load
ปริมาณ "ความคิด" ที่ผู้ใช้ต้องใช้ตีความข้อมูลบนจอ — list ยาวไม่มีการจัดกลุ่มทำให้ต้องคิดเยอะขึ้นว่าอันไหนเป็นของวันไหน
11

Auto-mark-read + debounce/throttle

หลักการ

Batch/rate-limit side effect ที่มองเห็นได้จากภายนอก (เขียน DB + เรียก API บุคคลที่สาม) แทนที่จะยิงทีละครั้งต่อ event ดิบ โดยเฉพาะเมื่อต้นทาง event ถี่อยู่แล้ว (SSE poll ทุก 500ms)

สาเหตุ

อยาก mark-as-read อัตโนมัติตอนแอดมินเปิดแชทค้างไว้แล้วมีข้อความใหม่เข้า แต่ยิงตรงๆ ทุกครั้งที่ message เปลี่ยนจะเรียก LINE API/เขียน DB ถี่เกินจำเป็นตอนลูกค้าทักรัวๆ

// feedback ที่ตาเห็น (unread dot หาย) = ทันที ไม่มีความเสี่ยงเพราะไม่ยิง network
// การยิงจริง = debounce รอนิ่ง 1 วิ + throttle floor ห้ามถี่กว่า 3 วิ (ใช้ useRef จำเวลายิงล่าสุด)
Pro
  • มีเพดานความถี่ชัดเจนแม้ทักต่อเนื่องยาวแค่ไหนก็ตาม (debounce เพียวๆ ไม่การันตีเพดานนี้)
  • ไม่มีความเสี่ยง "data หาย" เลย เพราะไม่ต้องมี server-side cache — ทุกอย่างเป็นแค่ timer ฝั่ง browser worst case แค่ยัง mark ไม่ทัน ไม่ใช่ข้อมูลหาย
Con
  • สถานะ "อ่านแล้ว" จริงที่ sync ไป LINE อาจดีเลย์ได้ถึงไม่กี่วินาที
  • logic ของ effect ซับซ้อนขึ้น (ต้องมั่นใจเรื่อง race ตอนสลับแชทเร็วๆ — สุดท้าย React's effect cleanup จัดการให้แล้วโดยไม่ต้องเขียนโค้ดกันเพิ่ม)
ศัพท์เทคนิค
Debounce
รอจนกว่า event จะ "นิ่ง" (ไม่เกิดซ้ำ) ครบเวลาที่กำหนดค่อยยิงจริงครั้งเดียว — ถ้ามี event ใหม่เข้ามาอีกระหว่างนั้นจะรีเซ็ตนับใหม่
Throttle
จำกัดไม่ให้ยิงถี่กว่าเวลาที่กำหนด ไม่ว่า event จะเข้ามาถี่แค่ไหนก็ตาม — มีเพดาน (floor) ตายตัวที่ debounce เพียวๆไม่มี
useRef
Hook ของ React ใช้เก็บค่าที่ "จำข้ามการ re-render" ได้ โดยไม่ทำให้ component re-render ซ้ำ — ในที่นี้ใช้จำเวลายิงล่าสุด

Test coverage 97%

หลักการ

เทสต้อง verify business behavior จริง ไม่ใช่ปั้นตัวเลข — ดึง pure logic ออกจากโค้ดที่ผูกกับ framework เพื่อเทสได้โดยไม่ต้องพึ่ง test infra หนักๆ และเพิ่ม infra (RTL/jsdom) เฉพาะตอนวัดแล้วเจอว่าจำเป็นจริง ไม่ใช่เดาไว้ก่อน

สาเหตุ

coverage เริ่มต้นแค่ 25.9% — DB layer และ React admin console (จุดที่เกิดบั๊กจริงทุกตัวในเซสชันนี้) แทบไม่มีเทสเลย

// ลำดับ: DB layer → routes ที่ยังไม่มีเทส → แยก pure function ออกจาก hooks/page แล้ววัดผล → ค่อยเพิ่ม RTL/jsdom เฉพาะส่วนที่ยังขาด
// ล็อกด้วย coverage threshold 80% ใน vitest.config.ts กันตกในอนาคต
Pro
  • 97% ด้วยเทสที่ตรวจ behavior จริงทุกตัว (125 tests) ไม่ใช่เทสเปล่าๆ เพื่อเลขสวย
  • วิธี "วัดก่อนเพิ่ม infra" กันไม่ให้ลงทุน RTL เกินจำเป็นตั้งแต่ต้น
  • ตั้ง threshold บังคับไว้แล้ว — ถ้า coverage ตกในอนาคต npm run test:coverage จะ fail ทันที ไม่ใช่แค่วัดครั้งเดียวจบ
Con
  • เพิ่ม dev dependency ใหม่ 2 ตัว (@testing-library/react, jsdom) และโค้ดเทสอีกก้อนใหญ่ที่ต้องดูแลต่อไป
  • บาง fixture ต้องระวังเรื่อง timezone-dependent flakiness เป็นพิเศษ (เจอจริงในข้อ 10)
ศัพท์เทคนิค
Test coverage
เปอร์เซ็นต์ของโค้ดที่ถูกรันผ่านตอนเทส — บอกแค่ว่า "รันผ่าน" ไม่ได้การันตีว่า "ถูกต้อง" (เทสห่วยๆก็ทำ coverage สูงได้)
RTL (React Testing Library) / jsdom
เครื่องมือจำลอง browser DOM บน Node เพื่อเทส React component ได้โดยไม่ต้องเปิด browser จริง
Coverage threshold
ค่าขั้นต่ำที่บังคับไว้ใน config เทส (เช่น 80%) ถ้า coverage ตกกว่านี้จะทำให้คำสั่งเทส fail ทันที — กันไม่ให้ coverage ค่อยๆลดลงแบบไม่รู้ตัวในอนาคต
Flakiness
เทสที่ผลลัพธ์ไม่แน่นอน — บางครั้งผ่าน บางครั้ง fail โดยไม่มีการเปลี่ยนโค้ดเลย (สาเหตุในที่นี้คือ timezone ของเครื่องรัน)
