React

  • SPA

  • Client-heavy application

Next.js

  • SEO
  • SSR
  • SSG
  • Routing
  • Performance / Initial Load
  • Fullstack Web Application

"ผมจะเลือกจาก Requirement มากกว่าความชอบครับ ถ้าเป็น Backoffice ที่ SEO ไม่สำคัญ React ก็เพียงพอ แต่ถ้าเป็น Public Web ที่ต้องการ SEO หรือ SSR ผมจะพิจารณา Next.js"

2Backend: Go vs NestJS

Go

ข้อดี

  • Performance สูง
  • Goroutine
  • Concurrency
  • Memory footprint ค่อนข้างต่ำ
  • เหมาะกับ High Concurrent System

เหมาะกับ

  • Realtime
  • Network Service
  • High Throughput
  • Microservice

NestJS

ข้อดี

  • TypeScript
  • Development เร็ว
  • Structure ชัด
  • Ecosystem ของ JS ดี
  • ทีม Frontend/JS สามารถต่อยอดง่าย
ห้ามตอบแบบนี้

"Go รับ Request ได้มากกว่า NestJS เสมอ" — เพราะ Performance ขึ้นกับ Workload, Database, Network, Architecture, Implementation, Hardware

คำตอบที่ดีกว่า

"ถ้า Requirement เป็น High Concurrency และทีมมีความสามารถด้าน Go ผมจะพิจารณา Go แต่ถ้าทีมถนัด TypeScript และ Requirement ไม่ได้ต้องการ Scale สูงมาก NestJS ก็อาจให้ Development Speed และ Maintainability ที่ดีกว่าครับ"

52ตัวอย่างคำตอบ Senior

คำถาม:

"ออกแบบ Chat ที่รองรับ 100,000 concurrent users"

ตอบ:

"ก่อนอื่นผมขอ Clarify ก่อนครับว่า 100,000 หมายถึง Concurrent WebSocket Connections หรือ Request per Second และมีประมาณกี่ Message ต่อวินาที เพราะ Architecture จะต่างกันครับ

ถ้าเป็น 100,000 Concurrent WebSocket Connections ผมจะใช้ Load Balancer กระจาย Connection ไปยัง WebSocket Server หลาย Instance โดยให้แต่ละ Instance เป็น Stateless ในส่วนของ Application State และเก็บ Connection Mapping ไว้ใน Shared Store เช่น Redis

Message ที่ส่งเข้ามาจะ Persist ลง Database เพื่อให้ Database เป็น Source of Truth จากนั้นผมจะพิจารณา Publish Event เข้า Kafka เพื่อ Decouple Message Processing และรองรับ Consumer หลายประเภท เช่น WebSocket Delivery, Notification และ Analytics

สำหรับ Reliability ผมจะระวัง Dual Write ระหว่าง Database กับ Kafka และพิจารณาใช้ Outbox Pattern

ส่วน Database จะออกแบบ Index ตาม Query Pattern เช่น roomId และ createdAt และพิจารณา Partitioning เมื่อข้อมูลมีขนาดใหญ่ขึ้น

หลังจากนั้นผมจะ Monitor WebSocket Connections, Message Latency, Kafka Consumer Lag, Database Throughput และ Error Rate เพื่อหา Bottleneck ก่อน Scale เพิ่มครับ"

53สิ่งที่ "ไม่ควร" ตอบ
❌

"100K users ต้องใช้ Microservice"

ดีกว่า

"ผมจะดู Bottleneck ก่อน แล้วค่อยแยก Service ที่ต้องการ Independent Scaling"

❌

"Message เยอะต้องใช้ NoSQL"

ดีกว่า

"ผมจะดู Access Pattern และ Query Requirement ก่อน แล้วพิจารณา SQL + Index/Partitioning ก่อน"

❌

"Kafka ทำให้ระบบเร็วขึ้น"

ดีกว่า

"Kafka ช่วย Buffer และ Decouple ทำให้ Scale Consumer ได้ แต่ไม่ได้ทำให้ Processing ของ Consumer เร็วขึ้นโดยตรง"

❌

"Redis ใช้เก็บ Message"

ดีกว่า

"Database เป็น Source of Truth ส่วน Redis ใช้ Cache หรือ Temporary State ตาม Requirement"

❌

"Go เร็วกว่า NestJS"

ดีกว่า

"Go อาจเหมาะกับ High Concurrency Workload แต่ต้องดู Requirement และ Team Capability ประกอบ"
