Part 1 · Rules

Rules คือ markdown ที่แยกกฎทีละเรื่อง

  • หนึ่งไฟล์ โฟกัสหนึ่งเรื่อง เช่น code-style.md, testing.md, security.md
  • ระดับโปรเจกต์: .claude/rules/ (ใช้บ่อยที่สุด)
  • ระดับผู้ใช้ (ทุกโปรเจกต์): ~/.claude/rules/
  • จัดเป็นโฟลเดอร์ย่อยได้ เช่น database/

ข้อดีข้อแรกคือกฎเป็น module ดูแลง่าย ข้อดีข้อที่สองสำคัญกว่า คือสั่งให้โหลดกฎเฉพาะตอนที่ทำงานกับไฟล์ที่เกี่ยวข้องได้

Part 1 · Rules

Rules มี 2 แบบ

แบบที่ 1 · Always loaded

ไม่มี paths ใน frontmatter โหลดตั้งแต่เริ่ม session ด้วย priority สูงเท่า CLAUDE.md เหมาะกับกฎสากลของโปรเจกต์

# code-style.md
- Use English for all comments
- Prefer functional approach
- Use strict typing everywhere
แบบที่ 2 · Path‑scoped

ใส่ paths เป็น glob pattern โหลดเมื่อ Claude อ่านไฟล์ที่ตรง pattern เท่านั้น

---
paths:
  - "src/api/**/*.ts"
  - "src/handlers/**/*.ts"
---
# API Design Rules
- Return consistent error shapes:
  { error: string, code: number }
- Log all requests with correlation IDs
- Rate limit headers on all routes

ใส่ description ใน frontmatter ด้วยเสมอ ไม่บังคับแต่แนะนำ เพื่อให้ Claude รู้ว่าไฟล์นี้มีไว้ทำอะไร

Part 2 · Auto‑memory

Claude ที่ลืมทุกอย่างทุกคืน

คุณใช้เวลา 20 นาทีอธิบายว่าโปรเจกต์ใช้ Vite, test อยู่ใน src/__tests__/, ชอบ named export, dev server รันที่พอร์ต 5173 วันรุ่งขึ้นเปิด session ใหม่ Claude จำอะไรไม่ได้เลย เหมือนคุยกับเพื่อนร่วมงานเก่งๆ ที่ความจำเสื่อมทุกคืน

Auto‑memory: Claude จดโน้ตให้ตัวเองระหว่างทำงาน

บันทึกวิธีที่คุณสั่งงาน เทคนิค debug สไตล์โค้ด และการตัดสินใจเชิงสถาปัตยกรรม แล้วเอากลับมาใช้ใน session ถัดไป เปิดไว้เป็นค่าเริ่มต้น ไม่ต้องตั้งค่าอะไร

CLAUDE.md + rules = ตำราเรียน

นักพัฒนาเป็นคนเขียน เป็นกฎที่ต้องทำตาม commit ลง git แชร์ทั้งทีม

"Use pnpm, not npm"
"Follow Airbnb React Style Guide"
"Never modify files in /generated/ or /dist/"
"Run tests with pnpm test --coverage"
Auto‑memory (MEMORY.md) = สมุดจดส่วนตัว

Claude เป็นคนเขียน เป็นสิ่งที่เรียนรู้และสังเกตเห็น อยู่ในเครื่องเราเท่านั้น ไม่ commit ลง git

"Build command for this project is pnpm build"
"Hydration mismatch was caused by using window
 during SSR without a useEffect guard"
"User prefers custom hooks over render props"
"E2E tests use Playwright, need dev server :5173"

Part 2 · Auto‑memory

Auto‑memory ทำงานอย่างไร

~/.claude/projects/
└── <project>/
    └── memory/
        ├── MEMORY.md          # index หลัก โหลดทุก session
        ├── debugging.md       # โน้ตเรื่อง debug
        └── api-conventions.md # การตัดสินใจเรื่อง API
  • หนึ่งสมุดต่อหนึ่ง repo ไม่ใช่ต่อ branch ทุก branch, worktree และโฟลเดอร์ย่อยใช้ร่วมกัน
  • ถ้าไม่ได้อยู่ใน git repo จะใช้ชื่อโฟลเดอร์ root ของโปรเจกต์
  • เห็นข้อความ Writing memory คือกำลังบันทึก และ Recalled memory คือกำลังดึงมาใช้
  • ไฟล์หัวข้อย่อยไม่โหลดตั้งแต่ต้น Claude อ่านเองเมื่อต้องใช้

ข้อจำกัด: โหลดแค่ 200 บรรทัดแรกของ MEMORY.md

ส่วนที่เกิน 200 บรรทัดจะไม่ถูกใช้ตอนเริ่มบทสนทนา Claude จึงย้ายรายละเอียดไปไว้ในไฟล์แยกตามหัวข้อ ขีดจำกัดนี้ใช้กับ MEMORY.md เท่านั้น CLAUDE.md โหลดทั้งไฟล์ไม่ว่ายาวแค่ไหน แต่ยิ่งสั้นยิ่งแม่นและสม่ำเสมอ

แนะนำให้เข้าไปดูโฟลเดอร์ memory อย่างน้อยเดือนละครั้ง แล้วแก้หรือลบสิ่งที่ไม่ถูกต้อง

Part 2 · Auto‑memory

ควบคุมและสั่งให้จำ

ตั้งค่า auto‑memory

/memory คือแผงควบคุม: ดูไฟล์ CLAUDE.md ทั้งหมดที่โหลดอยู่ (project, user, rules), สวิตช์เปิด/ปิด, เปิดไฟล์ memory ใน editor และเปิดดูโฟลเดอร์โน้ตของ Claude

// .claude/settings.json · ปิด auto-memory
{ "autoMemoryEnabled": false }

// user หรือ local settings · ย้ายที่เก็บ
{ "autoMemoryDirectory": "/path/to/custom/memory" }

# CI/CD: ไม่ให้ Claude จดเรื่อง build env
export CLAUDE_CODE_DISABLE_AUTO_MEMORY=1

Demo: สั่งให้จำเอง

> note that we use tabs for
  indentation, not spaces

Claude ค้นหา MEMORY.md ไม่เจอ จึงสร้างใหม่พร้อมไฟล์ย่อย มี frontmatter type: feedback และเหตุผล "user explicitly stated this is project's convention"

ประโยคอื่นที่ใช้ได้: "remember that we use pnpm, not npm", "save to memory that the API tests require a local Redis instance", "note that the staging environment uses port 3001"

ระบุปลายทางได้ เช่น "save this into CLAUDE.md" ถ้าไม่ระบุ Claude จะเลือกเอง

ใส่ใน CLAUDE.md หรือ rules?

สองอย่างนี้เปิดอยู่ตลอด token ของคำสั่งทำสไลด์จะนั่งกินที่ใน context แม้คุณแค่แก้ component ส่วน path‑scoped rules ก็ช่วยไม่ได้ เพราะงานพวกนี้ไม่ผูกกับไฟล์โค้ด

พิมพ์ prompt ใหม่ทุกครั้ง?

สองวันต่อมา prompt ก็เปลี่ยนไป ผลลัพธ์ไม่สม่ำเสมอ

อุปมาโรงพยาบาล

หมอทุกคนล้างมือ บันทึกเวชระเบียน แต่งกายตามกฎ นั่นคือ CLAUDE.md และ rules แต่เมื่อคนไข้ต้องผ่าตัดหัวใจ เราเรียกหมอหัวใจมาคนเดียว หมอทั่วไปแค่ต้องรู้ว่าเมื่อไหร่ควรเรียกผู้เชี่ยวชาญ Skills ทำงานแบบนี้

อีกภาพหนึ่ง: CLAUDE.md เหมือนแบกกล่องเครื่องมือทั้งกล่องไปทุกที่ จะไปซ่อมก๊อกน้ำรั่วก็ยังต้องหิ้วเลื่อยยนต์ ชุดเชื่อมเหล็ก และแปรงทาสีไปด้วย ทั้งที่ token ใน context window เป็นพื้นที่ราคาแพง

Part 3 · Skills

Agent Skills คือมาตรฐานเปิด

เดิมแต่ละผลิตภัณฑ์ AI เพิ่มความสามารถด้วยชื่อและรูปแบบของตัวเอง Agent Skills จึงเกิดขึ้นเป็นมาตรฐานกลาง ตอนนี้ Cursor, GitHub Copilot, Gemini CLI และ Claude Code ใช้แล้ว

Claude Code เพิ่มความสามารถบนมาตรฐานนี้ ได้แก่ การควบคุมว่าใครเรียกใช้ได้, รันใน sub‑agent และ dynamic context injection

ต่อยอดได้ เช่น แอปธนาคารที่มีหลาย domain (clients, fraud detection, payments) สร้าง skill ต่อ domain แล้วผูกกับ agent

Bundled skills ที่มีมาให้
  • /simplify รีวิวไฟล์ที่เพิ่งแก้ เรื่อง reuse, คุณภาพ, ประสิทธิภาพ โดยรัน review agent 3 ตัวพร้อมกันแล้วแก้ให้
  • /debug ไล่ปัญหาของ session จาก debug log
  • /loop, /batch, /claude-api

ก่อนสร้าง skill เอง ให้เช็คใน docs ก่อนว่ามีแบบ bundled อยู่แล้วหรือยัง

  • assets/ วัตถุดิบ เช่น template เอกสารหรือสไลด์

Part 3 · Skills

รัน skill ใน sub‑agent ด้วย context: fork

---
name: wiki-ask
description: Answer a question from
  the team wiki with [[page]] citations
argument-hint: "<question>"
context: fork
agent: Explore
---
Read index.md first, then open only the
relevant pages in wiki/.
Answer with [[page]] citations.
If the wiki has no coverage, say so.
Never fill gaps from model knowledge.
  • เนื้อหา skill กลายเป็น prompt ของ sub‑agent ที่มองไม่เห็นบทสนทนาหลัก
  • agent กำหนดสภาพแวดล้อม (model, tools, permissions) ถ้าไม่ใส่จะใช้ general-purpose
  • Explore มีแต่ tools แบบอ่านอย่างเดียว เหมาะกับงานค้นและอ่าน
  • sub‑agent เปิดอ่าน wiki กี่หน้าก็ได้ แต่ส่งกลับมาแค่คำตอบพร้อมอ้างอิง context หลักจึงไม่บวม

Skillความรู้เฉพาะงาน, workflow หรือเอกสารอ้างอิงที่ใช้เมื่อจำเป็นขั้นตอนที่ทำซ้ำ, domain playbook, เอกสารภายในrelease skill ที่พาทำ version bump, อัปเดต changelog, tag และ publish artifact

Part 4 · Commands (legacy)

Command คือ markdown ไฟล์เดียวที่กลายเป็น slash command

.claude/commands/review.md  →  /review
.claude/commands/commit.md  →  /commit
.claude/commands/deploy.md  →  /deploy

ชื่อไฟล์ (ตัด .md) คือชื่อ command ไม่ต้อง compile ไม่ต้องลงทะเบียน วางไฟล์ถูกที่ก็ใช้ได้เลย

Skills คือรุ่นถัดไปของ commands: command ต้องให้ผู้ใช้พิมพ์เรียกเสมอ ส่วน skill ให้ Claude ค้นเจอและเรียกเองได้เมื่องานตรงกับ description

ถูก deprecate แล้วหรือยัง? ใช่
"Custom commands have been merged into skills. A file at .claude/commands/review.md and a skill at .claude/skills/review/SKILL.md both create /review and work the same way. Your existing .claude/commands/ files keep working. Skills add optional features."
  • command เดิมยังใช้ได้ และรองรับ frontmatter แบบเดียวกับ skill
  • ถ้าชื่อซ้ำกัน skill ชนะ
  • งานใหม่ควรเป็น skill
  • community กำลังย้าย แม้แต่ repo plugins ทางการก็ยังมี issue เรื่อง plugin ที่ใช้ commands อยู่

เริ่มจากตรงไหนดี

1. ผ่า CLAUDE.md

เหลือแค่กฎสากลใน CLAUDE.md ย้ายเรื่องเฉพาะทางไป .claude/rules/ และใส่ paths ให้กฎที่ผูกกับโฟลเดอร์

2. ดูแล auto‑memory

เปิดดูโฟลเดอร์ memory เดือนละครั้ง ให้ MEMORY.md อยู่ใต้ 200 บรรทัด

3. หางานที่ทำซ้ำ

เช่น สรุปสถานะ daily standup จาก git log, วิเคราะห์ issue, ออก release แล้วแปลงเป็น skill เพื่อให้ได้ผลลัพธ์รูปแบบเดิมทุกครั้ง

4. ย้าย commands ไป skills

ถ้า repo ยังใช้ .claude/commands/ ให้ทยอยย้ายเป็น skill เพื่อได้ auto‑discovery และ sub‑agent
