1. คำถามสัมภาษณ์ตาม Stack

Next.js

  • SSR vs SSG vs ISR เลือกใช้ยังไงกับหน้าที่ต้องแสดงประวัติแชท/ข้อความ realtime
  • API Routes ของ Next.js ใช้เป็น backend หลักไหม หรือแยก Node server ต่างหาก แล้วทำไมเลือกแบบนั้น
  • จัดการ session/auth ยังไงถ้า user ล็อกอินผ่าน LINE Login แล้วต้องผูกกับระบบของเราเอง

LINE OA / Chatbot Integration

  • Webhook จาก LINE Messaging API เข้ามา — validate signature (x-line-signature) ยังไง ป้องกัน spoofed request ยังไง
  • LINE webhook ต้องตอบ 200 ภายในเวลาสั้นๆ ไม่งั้น retry — design ยังไงให้ processing หนักๆ ไม่บล็อก response
  • reply token มีอายุจำกัดและใช้ได้ครั้งเดียว — ถ้ามี event ซ้ำ (LINE retry) deduplicate ยังไง
  • Rich menu / Flex message ออกแบบยังไงให้ maintain ง่าย
  • LINE userId ผูกกับ user ในระบบเรายังไง ถ้า user บล็อก/ปลดบล็อก OA ต้องจัดการ state ยังไง

Node.js Backend

  • Event-driven กับ webhook handler — ใช้ queue (BullMQ/RabbitMQ) หรือ fire-and-forget แบบไหน trade-off คืออะไร
  • ถ้า call LINE API แล้ว rate limit (429) จะ retry/backoff ยังไง
  • เขียน middleware verify webhook signature แบบ reusable ยังไง

PostgreSQL

  • schema design สำหรับ chat history — เก็บ message log แบบไหนไม่ให้ table โตจนช้า
  • index strategy สำหรับ query "ดึงข้อความล่าสุดของ user คนนี้" ให้เร็ว
  • เคยเจอ N+1 query ตอนโหลด conversation + user profile ไหม แก้ยังไง

Docker / DevOps

  • Dockerize Next.js app ยังไงให้ image เล็ก (multi-stage build)
  • local dev ต้อง expose webhook ให้ LINE เรียกได้ (ngrok) — จัดการ workflow dev ↔ LINE sandbox ยังไง
  • docker-compose ผูก Next.js + Node worker + Postgres เข้าด้วยกันยังไง ถ้า scale ต้องแยก service ไหน

System Design (โจทย์รวม)

"ออกแบบระบบที่ user คุยกับ LINE OA แล้ว AI ตอบกลับ พร้อมเก็บ history และมี dashboard ให้ admin ดู conversation" — วาด flow ตั้งแต่ webhook เข้า → queue → AI process → reply → บันทึก DB → sync ไป dashboard

2. Deep Dive: คำตอบที่ควรตอบได้ (ข้อ 1-4)

Next.js — คำตอบละเอียด

SSR vs SSG vs ISR: Chat history เป็นข้อมูล per-user เปลี่ยนตลอด → ไม่เหมาะ SSG/ISR (cache ผูกกับ user เดียวไม่ได้) ใช้ SSR สำหรับ initial load + client-side fetching (SWR/TanStack Query) สำหรับ pagination/realtime

API Routes เป็น backend หลักไหม: ขึ้นกับ scale — webhook ที่ต้อง process หนัก + queue ควรแยก Node server เพราะ API Routes รันบน serverless มี timeout จำกัด ไม่เหมาะ long-running worker Pattern ที่ดี: Next.js API Route รับ webhook แล้วโยนเข้า queue ทันที (ACK เร็ว) ส่วน worker แยก service ต่างหาก

Auth กับ LINE Login: LINE Login (OAuth) → verify id_token → ได้ LINE userId → map เข้า internal user table Session ฝั่งเราใช้ NextAuth/JWT แยกจาก LINE token (อายุสั้น ใช้แค่ตอน login)

LINE OA / Chatbot — คำตอบละเอียด

Validate signature: HMAC-SHA256 ของ raw body ด้วย Channel Secret ต้อง verify ด้วย raw body ก่อน parse JSON (ถ้า framework parse ก่อนแล้ว hash จะไม่ตรง — pitfall จริงที่พลาดบ่อย)

Reply เร็ว + processing หนัก: webhook handler validate + push เข้า queue + ตอบ 200 ทันที Worker แยก process แล้วเรียก LINE Reply/Push API แบบ async

Reply token ใช้ครั้งเดียว + event ซ้ำ: deduplicate ด้วย webhookEventId เก็บ Redis/DB TTL สั้น ถ้าเคยเห็นแล้ว skip

Rich menu/Flex message: แยกเป็น template builder function ต่อ message type ไม่ hardcode JSON กระจาย

LINE userId ผูก + สถานะบล็อก: mapping table แยกจาก user table หลัก handle event follow/unfollow เพื่อไม่ยิง Push API ไปหา user ที่บล็อกแล้ว

Node.js Backend — คำตอบละเอียด

Queue vs fire-and-forget: Fire-and-forget เสี่ยงข้อมูลหายถ้า process crash Queue (BullMQ/Redis) ให้ retry + persistence + concurrency control คุ้มกว่าสำหรับ chat log ที่ห้ามข้อมูลหาย

Rate limit 429: exponential backoff with jitter ไม่ retry ทันที (จะโดน rate limit ซ้ำเป็น loop)

Middleware reusable: แยก verifyLineSignature middleware ออกจาก business logic เพื่อเทสได้อิสระและ reuse ได้หลาย endpoint

PostgreSQL — คำตอบละเอียด

Schema ไม่ให้โตช้า: Partition ตาม created_at (native Postgres partitioning) query ข้อความล่าสุดกระทบ partition เดียว แยก hot data (messages) จาก cold data (attachments/metadata)

Index strategy: Composite index (line_user_id, created_at DESC) ใช้ keyset pagination แทน OFFSET ตอนข้อมูลเยอะ

N+1 query: แก้ด้วย JOIN ครั้งเดียว หรือ batch fetch (WHERE id IN (...)) ระวัง ORM (Prisma) include ที่ทำให้เกิด N+1 ใน loop โดยไม่ตั้งใจ — เช็ค generated SQL จริงเสมอ

3. SQL vs NoSQL สำหรับ Chat Message — บทเรียนสำคัญ

Assumption ที่มักผิด (และมักถูกถามแบบฝัง assumption นี้ไว้ในคำถาม):
  1. "Message หลายรูปแบบ → ต้อง NoSQL"
  2. "ข้อมูลเยอะขึ้น SQL query ช้ากว่า NoSQL"

ทำไม assumption ผิด

  • เรื่อง schema หลายรูปแบบ: แก้ด้วย JSONB column ใน Postgres ได้ — เก็บ structured column (conversation_id, sender_id, created_at) สำหรับ index/join/transaction ปกติ ส่วน payload ที่ต่างกันตาม message type เก็บใน JSONB ได้เลย ไม่ต้อง migrate schema ทุกครั้งที่เพิ่ม type ใหม่
  • เรื่องความเร็ว: ความช้าไม่ได้มาจาก "เป็น SQL" แต่มาจาก indexing/partitioning Pattern ของ chat คือ "ดึง N ข้อความล่าสุดของ conversation" — ทำนายได้ 100% เหมาะกับ B-tree index + partitioning มาก ได้ sub-millisecond แม้ table มีพันล้าน row ข้อได้เปรียบจริงของ NoSQL คือ horizontal write scaling แบบ native ไม่ใช่ read speed

ตัวอย่าง schema แบบ hybrid

CREATE TABLE messages (
  id BIGINT PRIMARY KEY,
  conversation_id BIGINT NOT NULL,
  sender_id BIGINT NOT NULL,
  message_type TEXT NOT NULL,  -- 'text' | 'image' | 'flex' | 'sticker' | 'location'
  payload JSONB NOT NULL,       -- โครงสร้างต่างกันตาม type ได้เสรี
  created_at TIMESTAMPTZ NOT NULL
);
-- index: (conversation_id, created_at DESC)

เกณฑ์เลือกจริง

เกณฑ์Postgres (JSONB)NoSQL (Cassandra/DynamoDB/Mongo)
Write throughputหลักพัน-หมื่น msg/secหลักแสน-ล้าน msg/sec ต่อเนื่อง (Discord/WhatsApp scale)
Join กับ user/order/billing✅ จำเป็น❌ ต้อง denormalize เอง
Transaction (mark-as-read + unread count)✅ ACID nativeต้องจัดการ consistency เอง
Multi-region active-activeยากกว่า (Citus/manual sharding)✅ native
Ops team ดูแล distributed DBไม่ต้องต้องมีทีมดูแล cluster
Recommendation: อยู่กับ Postgres + JSONB + partitioning + composite index จนกว่าจะมี pain point จริง (ตัวเลข write throughput ที่วัดแล้วเกินกำลัง single node) — ย้ายไป NoSQL ล่วงหน้าคือ premature optimization

ระดับคำถามนี้ในการสัมภาษณ์

ถ้าถามแบบฝัง assumption ("chat ต้อง NoSQL เพราะ...") ถือเป็นคำถามระดับ MID-LEVEL — สัญญาณ senior จริงคือจับ assumption ผิดได้ก่อนตอบ ไม่ใช่แค่เลือกฝั่งถูก การยกระดับเป็น senior ต้องถามแบบ open-ended + follow-up เรื่อง partition key design / ตัวเลข traffic จริง

4. Prep Checklist — จุดที่ไม่ถนัด (SQL / Docker / K8s)

SQL HIGH ROI

  • JOIN types: INNER vs LEFT vs RIGHT + ตัวอย่างจริง (LEFT JOIN หา user ที่ยังไม่เคยสั่งซื้อ)
  • Index: B-tree เบื้องหลังคร่าวๆ, composite index ลำดับ column สำคัญ (WHERE a=1 AND b=2 → index (a,b))
  • N+1 query: อธิบาย + วิธีแก้ (JOIN, batch fetch, DataLoader)
  • Transaction/ACID: อธิบายด้วยตัวอย่างจริง ไม่ใช่ท่องนิยาม
  • Normalization: 1NF/2NF/3NF คร่าวๆ + เหตุผล denormalize เพื่อ performance
  • เขียนมือ: GROUP BY + HAVING, subquery, EXISTS vs IN
  • Pagination: LIMIT/OFFSET vs keyset pagination + trade-off
  • EXPLAIN ANALYZE ใช้ debug slow query
กับดัก: สับสน WHERE vs HAVING (WHERE filter ก่อน GROUP BY, HAVING filter หลัง) / ลืมพูด trade-off ว่า index ช่วย read แต่ทำให้ write ช้าลง

Docker MID ROI

  • Image vs Container ต่างกันยังไง
  • Dockerfile layer caching — ทำไม COPY package.json ก่อน npm install แล้วค่อย COPY . .
  • Multi-stage build — ลด image size, ไม่เอา build tool ไปติด production image
  • Volume vs Bind mount
  • docker-compose: depends_on รอ container start ไม่ใช่รอ service "พร้อม" จริง

Kubernetes MID ROI (concept พอ)

  • Pod — unit เล็กที่สุด มักมี 1 container
  • Deployment — จัดการ replica, rolling update
  • Service — ClusterIP/NodePort/LoadBalancer ต่างกันยังไง
  • ConfigMap/Secret — แยก config/credential จาก image
  • Ingress — routing HTTP เข้า cluster
  • HPA — scale ตาม CPU/memory
  • Liveness vs Readiness probe (restart ถ้าตาย vs ไม่ส่ง traffic ถ้ายังไม่พร้อม)
  • Debug Pod crash loop: kubectl logs, kubectl describe pod
ถ้า K8s ไม่ได้ลงมือทำเองมาก่อน — พูดตรงๆ ว่า "เคยใช้ระดับ concept/deploy ผ่าน manifest คนอื่นเซ็ตไว้ แต่ยังไม่ได้ design cluster เอง" ดีกว่าเดาแล้วโป๊ะตอน follow-up
